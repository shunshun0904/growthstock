# 運用と保存先

予測結果・モデル・生データがどこに置かれ、どの頻度で更新されるか。

## 置き場と役割

| | 中身 | 置き場 | 更新 | なぜそこか |
|---|---|---|---|---|
| 今日の予測 | `public/data/predictions.json`（直近5営業日の全候補・寄与分解つき） | git → GitHub Pages | 平日夜 | 画面が直接読む静的ファイル。毎日まるごと上書きする |
| 画面用の追跡 | `public/data/prediction_history.json`（上位5件/日・400日で削除） | git | 平日夜 | 画面に出すぶんだけ。**長期の台帳ではない** |
| **長期の台帳** | 予測ログ（全候補・1行1銘柄） | **Google スプレッドシート** | 平日夜 | 手売買の記録を同じ行に書き足せる。実績の検証はここを正本にする |
| モデル本体（基準） | `model.txt` / `oof.parquet` | **GitHub Release（`data-raw`）** | 日曜の夜 | 2.7MB のバイナリを毎週コミットすると差分圧縮が効かず年138MB 膨らむ |
| モデル本体（追加4つ） | `<algo>_model.joblib` / `<algo>_oof.parquet` | **GitHub Release（`data-raw`）** | 日曜の夜 | 同上。合計2.7MB。meta.json だけ git に残す |
| モデルの素性 | `research/model/meta.json`（9KB） | git | 日曜の夜 | 過去のモデルが「どういうものだったか」を追えるようにする |
| 生データ | 日次バー・財務・信用残ほか | GitHub Release（`data-raw`） | 平日21:30 | 全期間の取得に2.5時間かかるため、差分だけ取って書き戻す |

## 動く順番

```
平日 21:30 JST  Update Data Store    J-Quants から差分取得 → Release へ
      ↓ 完了で起動
平日 22:00 頃   Predict Breakouts    Release からモデルと生データを取得
                                     → 鮮度チェック（1営業日より古ければ停止）
                                     → 予測データセット構築 → 採点
                                     → 上位10銘柄の詳細を取得（stocks.json）
                                     → スプレッドシートへ追記
                                     → コミット → Pages 再デプロイ

日曜 21:00 JST  Retrain Weekly       J-Quants から差分取得（日曜は取り込みが
                                     走らないので自分で取りに行く）
                                     → 鮮度チェック（2営業日より古ければ停止）
                                     → Release へ書き戻し → 学習
                                     → モデルを Release へ、meta.json を git へ
```

鮮度チェックを入れてあるのは、取り込みが失敗した日に黙って昨日と同じ候補を出したり、
先週のデータで学習し直したりするほうが害が大きいため。気づけないことが一番よくない。

## なぜ学習を週の境目に置くのか

予測は毎営業日の夜に出るが、モデルは**週に1度しか差し替えない**。しかも
差し替えるのは日曜の夜、つまり月〜金のどの予測も挟まない位置に置いてある。

週の途中で差し替えると、その日の候補が前日までと比較できなくなる。
スコアが動いたのが「相場が変わったから」なのか「モデルが変わったから」なのかを
切り分けられず、順位も較正確率もスコア帯の実績も、日をまたいで読めなくなる。

```
  日曜の夜   モデルを作り直す（予測はしない）
  月〜金の夜 5日とも同じモデルで採点する
```

この理由から、**日曜には予測を走らせていない**（`Retrain Weekly` を
`Predict Breakouts` の `workflow_run` に繋いでいない）。日曜に予測すると、
金曜引け基準の同じ候補が金曜夜とは別のモデルでもう一度出ることになり、
どちらを見ればよいのか分からなくなる。新しいモデルは月曜夜の予測から効く。

## ハイパーパラメータの探索

**毎週探索する**（`Retrain Weekly` の既定）。精度を優先する判断。

実測で約36分かかる（3プリセット × 50試行 × 5分割、pointwise のみ）。
本番モデルは `LGBMClassifier` なので LTR の探索は回さない。学習まで含めた
`Retrain Weekly` 全体は40〜45分の見込みで、タイムアウト180分に対して余裕がある。

引き換えに、特徴量も母集団も変えていないのに**パラメータが週ごとに動く**。
予測が変わったときに「相場が変わった」のか「パラメータが変わった」のかを
切り分けられなくなるのが唯一の副作用なので、`research/lgbm_params.json` の
差分を毎週の実行要約に出してある。何が動いたかは毎週その場で見える。
ファイル自体も毎週コミットされるので、git の履歴で遡れる。

## 母集団（何を採点しているか）

その日に**78週高値を更新した銘柄だけ**が候補になる（`build_dataset.py` の
`POPULATION = "breakout"`）。直前20営業日に更新が無い日だけを「新規のブレイク」と
みなすので、同じ上昇局面で高値更新が続いても1件にまとまる。1日あたり数件。

その日の引け後に採点し、翌営業日に買うかを判断するための出力。

### ETF・ETN・REIT が候補に混ざるのは既知（2026-09-11 時点で意図的に放置）

市場区分によるフィルタは掛けていない（`mkt_code` は特徴量として使うだけ）。
そのため上場投信の類も母集団に入り、**スコア上位5%の41.7%を占める**。
母集団では7.6%しかないので5.5倍の過剰代表。不具合ではない。

| | 母集団 | 上位5% | 倍率 |
|---|---:|---:|---:|
| ETF等（`mkt_code == 109`）の比率 | 7.6% | 41.7% | 5.5x |
| ボラ中央値 | 1.84% | 0.99% | — |

**機構**: ボラ正規化ラベルのしきい値は `1.2 × σ × √60` なので、低ボラほど
バーが低い（ボラ0.88%なら必要上昇8.2%、6.31%なら58.7%）。ETF は分散された
バスケットで構造的に低ボラ（中央値0.97% / 株式2.04%）なため、正例になりやすい。
株式だけに限ってもボラ十分位で正例率が単調に 31.2% -> 8.3% と落ちる。

ランダムウォークなら到達確率はボラによらず一定のはずで、この勾配が出るのは
**ボラの平均回帰**が効いているためと考えられる（直近20日が高ボラな銘柄は
将来ボラが下がりやすくバーに届かない、低ボラ銘柄は逆）。これは未検証の仮説。

**放置してよい理由**: 実収益（`ref_end`、ラベル非依存）で見ると優位性は
ETF 由来ではない。外してもほぼ変わらない。

| | 母集団 | 上位5% | 差 |
|---|---:|---:|---:|
| ETF込み（現行） | +3.41% | +5.86% | +2.45pt |
| 株式のみ | +3.36% | +5.66% [+4.40, +6.89] | +2.30pt |

上位5%の中でも株式部分（+6.71%）のほうが ETF 部分（+4.67%）より良い。
実収益はボラ十分位ともほぼ無関係（十分位0で+3.39%、十分位9で+2.24%、単調ですらない）。

> **2026-09-17 追記: 上の「株式部分のほうが良い」は、いまの物差しでは逆転する。**
> 当時は全期間プールの上位5%・終値買い・60営業日（`ref_end`）で測っていた。
> 運用の物差し（翌営業日の寄り買い・40営業日・しきい値は過去の窓だけから決める）
> で測り直した結果は下の節。

### 測り直し（2026-09-17 / `research/exp/e17_etf.py`）

物差しを運用に合わせ、種3個の確率平均で測り直した。

**上位10%に選ばれた2,000件の内訳**（現行＝ETF込みで学習・採点）

| | 件数 | 構成比 | 実収益 中央 | 平均 | 勝率 | 25%分位 |
|---|---:|---:|---:|---:|---:|---:|
| ETF等 | 502 | 25.1% | **+2.79%** | +2.38% | **67.7%** | **-1.73%** |
| 株式等 | 1,498 | 74.9% | +2.24% | **+3.58%** | 59.7% | -3.62% |
| 全体 | 2,000 | 100% | +2.52% | +3.28% | 61.7% | -3.18% |

**ETF のほうが中央値も勝率も高く、下振れも浅い。** 株式のほうが平均は高い
（裾が厚い）。「安定した少額の利益」を狙うなら ETF は外すべきではない。

**学習から外しても効果は無い**（評価母集団を揃えた比較）

| 条件 | 窓平均 | 標準誤差 | 勝ち窓 | 最悪の窓 |
|---|---:|---:|---:|---:|
| A  学習=全部 / 評価=全部（現行） | +0.80pt | 0.32 | 7/9 | -0.73pt |
| A' 学習=全部 / 評価=株式のみ | +1.17pt | 0.26 | 9/9 | +0.17pt |
| B  学習=株式 / 評価=株式のみ | +1.28pt | 0.33 | 9/9 | +0.22pt |

A' と B の差は **+0.11pt / z=0.27 で差なし**。つまり **ETF を学習データから
外す意味は無い**（外すなら候補から落とすだけでよく、再学習は不要）。

A と A' の差（+0.37pt / z=0.90）も足切りを越えないが、勝ち窓が 7/9 → 9/9、
最悪の窓が -0.73pt → +0.17pt に変わる。ただし勝率は 61.7% → 57.8% に**落ちる**。
安定性を取るか、負ける窓を消すかのトレードオフで、平均リターンはほぼ同じ
（+3.28% → +3.22%）。

**上位10%に占める ETF 比率は窓ごとに 5.8%〜57.8% と大きく振れる。**
買う対象の構成が週によって入れ替わるので、そこが気になるなら外す理由になる。

**読むときの注意**: 正例率はボラで大きく歪むが実収益は歪まない。つまり画面と
スプレッドシートの**較正確率・帯の正例率は、低ボラ銘柄で系統的に楽観側にずれる**。
帯の実収益（`bandEndMedian`）のほうが素直に読める。

**外したくなったら**: 再学習は不要（上の A' と B に差が無い）。日次予測の
候補から `mkt_code == 109` を落とし、スコア帯と較正表をその母集団で
作り直すだけでよい。学習データはそのままでよい。

**スプレッドシートでの見分け方**: 業種が「その他」、時価総額が空欄。

## スプレッドシートの列

このパイプラインが書くのは左側の列だけで、**右側の記入欄には一切書き込まない**。

- 書く（追記時に1度）: 予測日 / コード / 銘柄名 / 業種 / 順位 / 候補数 / スコア / 帯 /
  較正確率% / 帯の正例率% / 帯の実収益% / 帯の勝率% / 必要上昇率% / 予測時株価 /
  時価総額 / 売買代金 / 日次ボラ% / 20日リターン% / 地合い寄与 / 銘柄固有寄与 / PER / PBR
- 書く（モデル別・追記時に1度）: LGB% / XGB% / CAT% / LR% / NN% /
  LGBスコア / XGBスコア / CATスコア / LRスコア / NNスコア / 一致(上位10%)
- 毎回更新: 現在値 / 騰落率% / 経過営業日
- **触らない（記入欄）**: 建値 / 株数 / 手仕舞い日 / 手仕舞い値 / 損益 / メモ

列は**見出しの名前で探す**。途中に自分用の列を挿しても壊れない。
行は追記のみで、既存行を作り直さない（作り直すと手入力が消える）。

### モデル別の列の読み方

2種類ある。

| 列 | 中身 | 使い方 |
| --- | --- | --- |
| `LGB%` など | そのモデル自身の**過去スコア分布での位置**（0〜100）。画面の棒グラフと同じ値 | **モデルをまたいで比べられるのはこちらだけ** |
| `LGBスコア` など | モデルが出した**生の値** | 同じモデルの中で日をまたいで追う／自分でしきい値を引き直す |

**生スコアはモデル間で大小を比べてはいけない。** 実例（2026-09-11 の1699）。

| | LGB | XGB | CAT | LR | NN |
| --- | ---: | ---: | ---: | ---: | ---: |
| 位置% | 90.3 | 89.4 | 94.4 | 54.4 | 84.3 |
| 生スコア | 0.535 | 0.474 | 0.615 | 0.500 | 0.294 |

NN の生スコア 0.294 は LR の 0.500 より小さいが、**位置は NN 84.3 > LR 54.4**。
学習器ごとに確率の出方が違うためで、生スコアの大小には意味がない。

位置だけだと後から別のしきい値で切り直せない（順位に潰れている）ので、
生スコアも併せて残してある。

既存の `スコア` 列は基準モデル（LightGBM）の生スコアで、`LGBスコア` と同じ値。
運用開始時から入っている列なので、過去行との連続性のために残してある。

`一致(上位10%)` は上位10%と見ているモデルの数（例 `3/5`）。独立した判定の
数え上げで、スコアを混ぜた値ではない。**平均は出していない** — 混ぜた数字を
1つ出すと、呼び名が何であれアンサンブルになるため。

`順位 / 帯 / スコア / 較正確率%` はすべて**基準モデル（LightGBM）**のもので、
`LGB%` と同じモデルを指す。モデル別の列は隣に並べる参考値で、順位には効かない。

読むときの注意（実測・`docs/MODEL_LINEUP.md`）。

- 木3つ（LGB / XGB / CAT）は互いに相関 0.80〜0.89、上位10%の重複 50〜58%。
  **揃って高くても独立した3票ではない**
- 木以外2つ（LR / NN）は互いに 0.823。塊をまたぐと 0.63〜0.71 に落ちる
- **塊をまたいで揃ったとき**だけ、見方の違うモデルが同じ結論に達したと読める

### 列が増えたとき

このパイプラインが書く列が増えたら、**見出し行の右端に自動で足される**
（`ensure_columns`）。途中に挿し込まないので、既存セルはずれず、記入欄の
中身は動かない。直近5営業日ぶんの既存行には、空のままのセルだけ埋める
（すでに値があるセルは手で直した可能性があるので触らない）。

並び順が気になるときは、**見出しを手でドラッグして動かしてよい**。
列は名前で探しているので、どこにあっても正しく書き込まれる
（名前そのものを変えると、その列は書き込み対象から外れる）。

## セットアップ（スプレッドシート）

1回だけ必要な作業。

1. Google Cloud のプロジェクトで **Google Sheets API** を有効にする
   （コンソール → APIとサービス → ライブラリ → "Google Sheets API" → 有効にする）
2. **サービスアカウント**を作る（IAMと管理 → サービスアカウント → 作成）。
   ロールは付けなくてよい（シート側の共有で権限を渡すため）
3. そのサービスアカウントの **鍵（JSON）** を作成してダウンロード
4. 予測ログ用のスプレッドシートを新規作成し、
   **サービスアカウントのメールアドレス**（`...@....iam.gserviceaccount.com`）に
   **編集者**として共有する
5. GitHub の Settings → Secrets and variables → Actions に登録する
   - `GOOGLE_SERVICE_ACCOUNT_JSON` … ダウンロードした JSON の中身をそのまま貼る
   - `GSHEET_ID` … シートURLの `/d/` と `/edit` の間の文字列

未設定の間は、この手順のステップだけ飛ばして日次予測は通常どおり動く。
設定した日から追記が始まる（**過去分は遡らない**）。

手元で内容だけ確かめるには通信しない確認モードがある。

```
python3 research/export_sheets.py --dry-run
```

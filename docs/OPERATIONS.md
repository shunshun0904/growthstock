# 運用と保存先

予測結果・モデル・生データがどこに置かれ、どの頻度で更新されるか。

## 置き場と役割

| | 中身 | 置き場 | 更新 | なぜそこか |
|---|---|---|---|---|
| 今日の予測 | `public/data/predictions.json`（直近5営業日の全候補・寄与分解つき） | git → GitHub Pages | 平日夜 | 画面が直接読む静的ファイル。毎日まるごと上書きする |
| 画面用の追跡 | `public/data/prediction_history.json`（上位5件/日・400日で削除） | git | 平日夜 | 画面に出すぶんだけ。**長期の台帳ではない** |
| **長期の台帳** | 予測ログ（全候補・1行1銘柄） | **Google スプレッドシート** | 平日夜 | 手売買の記録を同じ行に書き足せる。実績の検証はここを正本にする |
| モデル本体 | `model.txt` / `oof.parquet` | **GitHub Release（`data-raw`）** | 日曜の夜 | 2.7MB のバイナリを毎週コミットすると差分圧縮が効かず年138MB 膨らむ |
| モデルの素性 | `research/model/meta.json`（9KB） | git | 日曜の夜 | 過去のモデルが「どういうものだったか」を追えるようにする |
| 生データ | 日次バー・財務・信用残ほか | GitHub Release（`data-raw`） | 平日21:30 | 全期間の取得に2.5時間かかるため、差分だけ取って書き戻す |

## 動く順番

```
平日 21:30 JST  Update Data Store    J-Quants から差分取得 → Release へ
      ↓ 完了で起動
平日 22:00 頃   Predict Breakouts    Release からモデルと生データを取得
                                     → 鮮度チェック（1営業日より古ければ停止）
                                     → 予測データセット構築 → 採点
                                     → 上位10銘柄の詳細を取得（stocks.json）
                                     → スプレッドシートへ追記
                                     → コミット → Pages 再デプロイ

日曜 21:00 JST  Retrain Weekly       J-Quants から差分取得（日曜は取り込みが
                                     走らないので自分で取りに行く）
                                     → 鮮度チェック（2営業日より古ければ停止）
                                     → Release へ書き戻し → 学習
                                     → モデルを Release へ、meta.json を git へ
```

鮮度チェックを入れてあるのは、取り込みが失敗した日に黙って昨日と同じ候補を出したり、
先週のデータで学習し直したりするほうが害が大きいため。気づけないことが一番よくない。

## なぜ学習を週の境目に置くのか

予測は毎営業日の夜に出るが、モデルは**週に1度しか差し替えない**。しかも
差し替えるのは日曜の夜、つまり月〜金のどの予測も挟まない位置に置いてある。

週の途中で差し替えると、その日の候補が前日までと比較できなくなる。
スコアが動いたのが「相場が変わったから」なのか「モデルが変わったから」なのかを
切り分けられず、順位も較正確率もスコア帯の実績も、日をまたいで読めなくなる。

```
  日曜の夜   モデルを作り直す（予測はしない）
  月〜金の夜 5日とも同じモデルで採点する
```

この理由から、**日曜には予測を走らせていない**（`Retrain Weekly` を
`Predict Breakouts` の `workflow_run` に繋いでいない）。日曜に予測すると、
金曜引け基準の同じ候補が金曜夜とは別のモデルでもう一度出ることになり、
どちらを見ればよいのか分からなくなる。新しいモデルは月曜夜の予測から効く。

## ハイパーパラメータの探索

**毎週探索する**（`Retrain Weekly` の既定）。精度を優先する判断。

実測で約36分かかる（3プリセット × 50試行 × 5分割、pointwise のみ）。
本番モデルは `LGBMClassifier` なので LTR の探索は回さない。学習まで含めた
`Retrain Weekly` 全体は40〜45分の見込みで、タイムアウト180分に対して余裕がある。

引き換えに、特徴量も母集団も変えていないのに**パラメータが週ごとに動く**。
予測が変わったときに「相場が変わった」のか「パラメータが変わった」のかを
切り分けられなくなるのが唯一の副作用なので、`research/lgbm_params.json` の
差分を毎週の実行要約に出してある。何が動いたかは毎週その場で見える。
ファイル自体も毎週コミットされるので、git の履歴で遡れる。

## 母集団（何を採点しているか）

その日に**78週高値を更新した銘柄だけ**が候補になる（`build_dataset.py` の
`POPULATION = "breakout"`）。直前20営業日に更新が無い日だけを「新規のブレイク」と
みなすので、同じ上昇局面で高値更新が続いても1件にまとまる。1日あたり数件。

その日の引け後に採点し、翌営業日に買うかを判断するための出力。

## スプレッドシートの列

このパイプラインが書くのは左側の列だけで、**右側の記入欄には一切書き込まない**。

- 書く（追記時に1度）: 予測日 / コード / 銘柄名 / 業種 / 順位 / 候補数 / スコア / 帯 /
  較正確率% / 帯の正例率% / 帯の実収益% / 帯の勝率% / 必要上昇率% / 予測時株価 /
  時価総額 / 売買代金 / 日次ボラ% / 20日リターン% / 地合い寄与 / 銘柄固有寄与 / PER / PBR
- 毎回更新: 現在値 / 騰落率% / 経過営業日
- **触らない（記入欄）**: 建値 / 株数 / 手仕舞い日 / 手仕舞い値 / 損益 / メモ

列は**見出しの名前で探す**。途中に自分用の列を挿しても壊れない。
行は追記のみで、既存行を作り直さない（作り直すと手入力が消える）。

## セットアップ（スプレッドシート）

1回だけ必要な作業。

1. Google Cloud のプロジェクトで **Google Sheets API** を有効にする
   （コンソール → APIとサービス → ライブラリ → "Google Sheets API" → 有効にする）
2. **サービスアカウント**を作る（IAMと管理 → サービスアカウント → 作成）。
   ロールは付けなくてよい（シート側の共有で権限を渡すため）
3. そのサービスアカウントの **鍵（JSON）** を作成してダウンロード
4. 予測ログ用のスプレッドシートを新規作成し、
   **サービスアカウントのメールアドレス**（`...@....iam.gserviceaccount.com`）に
   **編集者**として共有する
5. GitHub の Settings → Secrets and variables → Actions に登録する
   - `GOOGLE_SERVICE_ACCOUNT_JSON` … ダウンロードした JSON の中身をそのまま貼る
   - `GSHEET_ID` … シートURLの `/d/` と `/edit` の間の文字列

未設定の間は、この手順のステップだけ飛ばして日次予測は通常どおり動く。
設定した日から追記が始まる（**過去分は遡らない**）。

手元で内容だけ確かめるには通信しない確認モードがある。

```
python3 research/export_sheets.py --dry-run
```

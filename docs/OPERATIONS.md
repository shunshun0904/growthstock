# 運用と保存先

予測結果・モデル・生データがどこに置かれ、どの頻度で更新されるか。

## 置き場と役割

| | 中身 | 置き場 | 更新 | なぜそこか |
|---|---|---|---|---|
| 今日の予測 | `public/data/predictions.json`（直近5営業日の全候補・寄与分解つき） | git → GitHub Pages | 平日夜 | 画面が直接読む静的ファイル。毎日まるごと上書きする |
| 画面用の追跡 | `public/data/prediction_history.json`（上位5件/日・400日で削除） | git | 平日夜 | 画面に出すぶんだけ。**長期の台帳ではない** |
| **長期の台帳** | 予測ログ（全候補・1行1銘柄） | **Google スプレッドシート** | 平日夜 | 手売買の記録を同じ行に書き足せる。実績の検証はここを正本にする |
| モデル本体（基準） | `model.txt` / `oof.parquet` | **GitHub Release（`data-raw`）** | 日曜の朝 | 2.7MB のバイナリを毎週コミットすると差分圧縮が効かず年138MB 膨らむ |
| モデル本体（追加4つ） | `<algo>_model.joblib` / `<algo>_oof.parquet` | **GitHub Release（`data-raw`）** | 日曜の朝 | 同上。合計2.7MB。meta.json だけ git に残す |
| モデルの素性 | `research/model/meta.json`（9KB） | git | 日曜の朝 | 過去のモデルが「どういうものだったか」を追えるようにする |
| 生データ | 日次バー・財務・信用残ほか | GitHub Release（`data-raw`） | 平日16:05 起動 | 全期間の取得に2.5時間かかるため、差分だけ取って書き戻す |
| 有報の年次財務 | `edinet_fin.parquet` / `edinet_companies.parquet` / `edinet_manifest.json` | GitHub Release（`data-raw`） | 毎日 10:05 起動 | EDINET DB は 100/日・900/月の枠しか無いので、毎日 85社ずつ差分で貯める（`docs/DATA_EDINETDB.md`）。**まだ研究用で、本番の特徴量には入っていない** |

## 動く順番

```
平日 16:05 JST  Update Data Store    当日の四本値・指数・TOPIX が出るまで待つ
                                     （締切18:00）
                                     → J-Quants から差分取得 → Release へ
      ↓ 完了で起動
                Predict Breakouts    Release からモデルと生データを取得
                                     → 鮮度チェック（1営業日より古ければ停止）
                                     → 予測データセット構築 → 採点
                                     → 上位10銘柄の詳細を取得（stocks.json）
                                     → スプレッドシートへ追記
                                     → コミット → Pages 再デプロイ

毎日 10:05 JST  Fetch EDINET DB      EDINET DB から年次財務を 85社ぶん取って
                                     Release へ（1社1リクエスト。月 850 で止まる）

日曜 09:05 JST  Retrain Weekly       J-Quants から差分取得（日曜は取り込みが
                                     走らないので自分で取りに行く）
                                     → 鮮度チェック（2営業日より古ければ停止）
                                     → Release へ書き戻し → 学習
                                     → モデルを Release へ、meta.json を git へ
```

**cron の時刻に起動はしない。** GitHub のスケジュール起動は実測で
+4時間01分 〜 +5時間37分 遅れる（下表）。実際はこうなる。

| | cron | 実際の起動 | 完了の見込み |
|---|---|---|---|
| Update Data Store | 平日 16:05 JST | 平日 20:06〜21:42 JST | 数分（実測1分35秒） |
| Retrain Weekly | 日曜 09:05 JST | **日曜 13:06〜14:42 JST** | 日曜 16:00〜19:45 JST |
| Fetch EDINET DB | 毎日 10:05 JST | 毎日 14:06〜15:42 JST（見込み） | 1〜2分（初回実測 1分10秒） |

学習は探索込みで3〜5時間かかる。**日曜の朝9時に見て「まだ始まっていない」のは
異常ではない** —— 実際に動き出すのは昼過ぎになる。

`Retrain Weekly` は 2026-09-19 に 21:00 JST から 09:05 JST へ12時間前倒しした。
遅延込みで完了が月曜の朝にずれ込んでいたため。使うのは金曜引けまでのデータで
土日に増えるものは無く、鮮度チェックも営業日で数えるので、朝でも夜でも判定は
同じ。月曜の予測までの余裕はむしろ増える。

鮮度チェックを入れてあるのは、取り込みが失敗した日に黙って昨日と同じ候補を出したり、
先週のデータで学習し直したりするほうが害が大きいため。気づけないことが一番よくない。

### 休場日はどうなるか

cron は平日に起動するので、祝日でもワークフローは動く。

| | 休場日の挙動 |
|---|---|
| Update Data Store | 待ちは締切で諦めて **exit 0**。営業日カレンダーに祝日は入らないので取得対象が無く、**成功**で終わる |
| Predict Breakouts | **営業日ゲートで飛ばす**（下記）。緑のまま「本日は非営業日」で終わる |
| 画面 | 前営業日の内容のまま据え置き |
| 台帳 | 追記なし（`(予測日, コード)` で重複排除） |

**鮮度チェックだけでは連休をさばけない。** 遅れを**平日**で数えており
（祝日カレンダーは意図的に持ち込んでいない。持ち込むと「更新が止まったのに
祝日だからと自分で言い訳する」余地ができる）、日次予測の許容は1営業日なので、
3連休では2日目・3日目が「遅れ2〜3営業日」で止まる。止まること自体は正しいが、
**正常な休場と本物の取り込み障害が同じ赤い×になる**。連休のたびに赤を見れば、
本物を見逃す訓練になってしまう。

そこで、**営業日かどうかを推測せずに受け取る**。

```
Update Data Store   J-Quants の営業日カレンダーを引く（ここだけが引いている）
                    → manifest.json の calendar に事実として書き残す
                       {"asOfJst": "2026-09-21", "isTradingDay": false,
                        "lastTradingDay": "2026-09-18"}
      ↓ Release 経由
Predict Breakouts   research/trading_day_gate.py がそれを読むだけ
                    → 非営業日なら以降のステップを飛ばして緑で終わる
```

予測側にカレンダーを持ち込むのではなく、既に知っている側から渡す形にしてある。
予測側が自分で「祝日だから」と言い訳できる余地は作っていない。

**飛ばすのは3条件がすべて揃ったときだけ。**

1. `calendar.isTradingDay` が**明示的に false**（`null` や欠損は飛ばさない）
2. 保存データの最終バー日 == `calendar.lastTradingDay`
   —— **ここが肝**。取り込みが壊れていれば保存データは直近の営業日に届いて
   いないので、休場日であっても飛ばさず、鮮度チェックで落とす
3. manifest が12時間以内に更新されている（取り込みが今日走ったこと）

どれか1つでも欠ければ通常どおり進む。**飛ばす側には倒さない。**
判断できない事情（manifest が読めない、バーが無い）もすべて「進む」に倒し、
ゲート自体は必ず exit 0 で返す。止めるかどうかは鮮度チェックの仕事のまま。

例：2026-09-21〜23（敬老の日・国民の休日・秋分の日）

| 日 | Update Data Store | Predict Breakouts |
|---|---|---|
| 9/21(月) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/22(火) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/23(水) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/24(木) | ✅ 09-24 を取得 | ✅ 新しい候補 |

### 起動時刻を 21:30 から 16:05 に前倒しした（2026-09-17）

**実際の公開が遅いのは J-Quants ではなく GitHub のせい**だった。
スケジュール起動が毎回4時間以上遅れている（実測）。

| ワークフロー | cron | 予定(UTC) | 実際の開始(UTC) | 遅れ |
|---|---|---|---|---|
| Update Data Store | `30 12` | 09-11 12:30 | 16:38 | +4h08m |
| | | 09-14 12:30 | 18:07 | +5h37m |
| | | 09-15 12:30 | 17:10 | +4h40m |
| | | 09-16 12:30 | 17:10 | +4h40m |
| Predict Breakouts | `0 14` | 09-14 14:00 | 19:08 | +5h08m |
| | | 09-15 14:00 | 18:02 | +4h02m |
| | | 09-16 14:00 | 18:01 | +4h01m |

7回とも4時間を切っていない。21:30 起動では画面の更新が**翌日2時台**になる
（09-16 の実績: データ 17:11 UTC ＝ 翌2:11 JST、予測 17:14 UTC ＝ 翌2:14 JST）。

遅れがこれだけ安定しているなら、cron を早く置いた時間だけ実際の公開も
早くなる。そこで大引け直後の 16:05 JST に移した。`:00` / `:30` は
世界中の cron が集中するので `:05` を選んでいる。

### J-Quants が当日データを出す時刻（実測・2026-09-18）

公式ドキュメント（jpx-jquants.com / jpx.gitbook.io）はこの作業環境から
読めない（egress ブロック）ので、`research/probe_update_time.py` を
16:00〜20:30 JST に30分間隔で回して実測した。

| 種別 | エンドポイント | 最初に行が返った時刻(JST) |
|---|---|---|
| 四本値 | `/equities/bars/daily` | **16:00 より前**（下記） |
| 銘柄マスタ | `/equities/master` | **16:00 より前**（下記） |
| 業種別指数 | `/indices/bars/daily` | 16:30:09 |
| TOPIX | `/indices/bars/daily/topix` | 16:30:09 |
| 決算開示 | `/fins/summary` | 18:00:37 |
| 信用残 | `/markets/margin-interest` | 20:30 までに出ず |

読むときの注意が3つある。

1. **四本値とマスタの「16:00」は上限であって実測値ではない。** 大引けが
   15:30 なので 16:00 から見始めたが、その最初の1回で既に出ていた。
   実際はもっと早い可能性がある。締め直すなら測り直しから。
2. **1日ぶんしか測っていない（n=1）。** 決算期や連休明けに遅れないとは
   言えない。締切に余裕を残してあるのはそのため。
3. **信用残が出なかったのは異常ではない。** 週次で、金曜ぶんが翌週に出る。
   対照に使った前営業日（木曜）も0行だったので、この実測では
   「叩き方が正しいか」の確認が取れていない。

四本値は 16:00:00 の時点で 4,451行/終値 4,201件あり、20:31 まで
増えなかった（後から追加される出方はしない）。

### 当日データが出るまで待つ

**定刻に起動してしまった日のために待つ**。前倒しすると、たまたま遅延が
小さかった日に「まだ当日データが無い」状態で走ることになる。
`research/wait_for_data.py` を取り込みの前に挟み、**四本値・業種別指数・
TOPIX** が出るまで待つ（締切 18:00 JST。実測 16:30 に対して1時間半の余裕）。

四本値だけでは足りない。`build_dataset` は業種別指数と TOPIX を
`merge_asof(direction="backward")` で結合するので、**その日の行が無いと
欠測にならず前日の値が入る**。気づけない形で質が落ちるので、ここは待つ。

決算開示（18:00）は待たない。1時間半の遅れに見合わないと判断した。
取りこぼしても失われはせず、翌営業日の取り込みで入る（下記）。
同じ日に入れたければ、ワークフローの `--feeds` に `fins` を足して
`--deadline` を 18:30 にすればよい。

締切まで出なくても**止めずに先へ進む** — 祝日・臨時休場はそもそも
当日データが存在せず、ここで落とすとその日だけパイプライン全体が
止まるため。古いデータで予測する事故は鮮度チェックが見ている。

### 公表前に叩いた日を「取得済み」にしない

差分取得の記録（`manifest.json` の `fetched_days`）は**行数ではなく
「その日を叩きに行ったか」**で付けている。財務のように開示が0件の日を
毎回叩き直さないためだが、そのままでは**公表前に叩いた日も取得済みに
なる**。`missing_days` は「候補 − 記録」なので、一度記録した日は二度と
候補に入らない。つまりその日のデータは永久に失われる。

21:30 起動のときは四本値・指数・財務がすべて出そろっていたので表に
出なかったが、**信用残では既に起きていた**。保存データを確認すると
記録は 2026-09-07 まであるのに、実データは 2026-08-28 が最後だった。
週次公表を待たずに叩いた週が、取得済みとして記録されて消えている。

そこで種別ごとに公表ラグを持たせた（`data_store.PUBLISH_LAG_DAYS`）。
**0件で返り、かつ公表ラグの中にある日は記録しない**ので、次回また
取りに行く。ラグを過ぎても0件ならそれは本当に0件（祝日・開示なし）と
みなして記録する — そうしないと永久に叩き続けることになる。

| 種別 | 猶予 | 理由 |
|---|---|---|
| 四本値・指数・TOPIX・財務・マスタ履歴 | 当日のみ | 同じ日のうちに出る |
| 信用残 | 10日 | 週次。金曜ぶんが翌週に出る |

この仕組みがあるので、16:05 起動で財務を待たなくてもデータは失われない
（1営業日遅れて入るだけ）。

### 信用残の穴を数え直した（2026-09-18）

記録を見ているだけでは気づけないので、保存データの側から数えた。
10年ぶん519週のうち、**32週**が空いていた（範囲内の30週＋直近2週）。
内訳は3つに分かれる。

| 原因 | 週数 | 取り直しで戻ったか |
|---|---|---|
| 公表ラグ（上節） | 2 | 戻った |
| 叩く日が違っていた（下記 (1)） | 23 | 17週が戻った。残り6週は (3) |
| J-Quants に元々無い（下記 (3)） | 13 | 戻らない（7週＋上の6週） |

**(1) 金曜が祝日の週（23週）。** 残高はその週の**最終営業日**時点のもの。
ふつうは金曜だが、金曜が休場なら木曜になる。旧コードは「金曜を全部足し、
金曜が無い週はその週の適当な日を足す」としていて、この「適当な日」が
週の**先頭**（多くは月曜）だった。月曜を叩いて0件、そのまま取得済み。
`jq_bulk.margin_candidates()` に切り出して、週の最終営業日を選ぶようにした。
`fetch_margin` と差分取得の2か所に同じ間引きを書いていたのも、ここで1つに
まとめてある（二重に持つとずれる）。

**(2) 問い合わせ自体が失敗した日。** これは上の30週を**説明しない** ——
コードを読んでいて見つけた別経路で、実際に起きた形跡は確認していない。
`_fetch_by_day` は失敗した日を読み飛ばして件数だけ出していたが、記録は
要求した日すべてに付いていた。一過性の 503 で1営業日ぶんが永久に失われる
経路なので、失敗した日を `LAST_FAILED_DAYS` で持ち回して記録から外した。

**(3) J-Quants 側に元々無い週（13週）。** (1) と公表ラグを直して全期間を
取り直した結果、**19週が戻り**、13週は取り直しても0件のままだった。

```
2017-05-02(火) 2018-01-05(金) 2018-05-02(水) 2019-01-04(金) 2019-12-30(月)
2020-05-08(金) 2021-05-07(金) 2022-05-06(金) 2023-05-02(火) 2024-01-05(金)
2024-12-30(月) 2025-12-30(火) 2026-05-08(金)
```

**13週すべてが GW・正月明け・年末の、営業日が1〜2日しかない週**。
例外なくこのパターンなので、J-Quants がこれらの週の残高を公表していない
ものと判断した（公式ドキュメントが読めないため、根拠は実測のこの規則性
だけ）。公表ラグ（10日）を過ぎた過去の週なので「本当に0件」として記録され、
毎回叩き直すことにはならない。

### 失われたぶんを取り直す

**自動では戻らない。** 記録済みの日は候補に入らないので、記録を外してやる
必要がある。`Update Data Store` を手動起動し、`forget` に種別を入れる
（範囲を絞るなら `forget_from` に開始日）。

```
forget      = margin
forget_from =            ← 空なら全期間
```

`--forget` は**取得記録だけ**を外す（`--reset` と違って parquet は消さない）
ので、取り直せなければ現状のまま何も変わらない。

信用残は `credit_ratio` の元で、staleness の上限が無い。実データが
2026-08-28 で止まっていたため、8月29日以降のサンプルはすべて 08-28 の値を
使っていた。2026-09-18 の取り直しで **486週 → 505週**（2016-10-07 〜
2026-09-11）になり、直近まで埋まった。所要は519週ぶんで約14分。

## なぜ学習を週の境目に置くのか

予測は毎営業日の夜に出るが、モデルは**週に1度しか差し替えない**。しかも
差し替えるのは日曜、つまり月〜金のどの予測も挟まない位置に置いてある。

週の途中で差し替えると、その日の候補が前日までと比較できなくなる。
スコアが動いたのが「相場が変わったから」なのか「モデルが変わったから」なのかを
切り分けられず、順位も較正確率もスコア帯の実績も、日をまたいで読めなくなる。

```
  日曜の朝   モデルを作り直す（予測はしない）
  月〜金の夜 5日とも同じモデルで採点する
```

この理由から、**日曜には予測を走らせていない**（`Retrain Weekly` を
`Predict Breakouts` の `workflow_run` に繋いでいない）。日曜に予測すると、
金曜引け基準の同じ候補が金曜夜とは別のモデルでもう一度出ることになり、
どちらを見ればよいのか分からなくなる。新しいモデルは月曜夜の予測から効く。

## ハイパーパラメータの探索

**毎週探索する**（`Retrain Weekly` の既定）。精度を優先する判断。

実測で約36分かかる（3プリセット × 50試行 × 5分割、pointwise のみ）。
本番モデルは `LGBMClassifier` なので LTR の探索は回さない。

これに画面へ並べる追加4モデル（xgb / cat / logit / mlp）の探索が続く
（実測127分。`logit` だけで70分を占める）。学習まで含めた `Retrain Weekly`
全体は**3〜5時間**で、ジョブのタイムアウト330分に対しては収まるが余裕は大きくない。
追加4モデルの探索は `continue-on-error` かつ試行 DB を持ち回すので、
打ち切られても基準モデルは出るし、同じ週の再実行で続きから走る。

**探索は学習と同じ列で行う**（2026-09-23、運用者の指示）。本番の列は
`features.DEFAULT_PRESET`（`all_plus`・205列）で、LightGBM の探索
（`research/tune_presets.txt` の先頭）も追加4モデルの探索
（`research/exp/e15_tune_all.py`）もこの列を使う。探索の記録には列の指紋が残り、
学習側が突き合わせる。

- 本番モデル（`train_production.py`）: 学習する列で探索したパラメータが無い・
  違う列で探索したものなら**学習を止める**。日次の予測は先週のモデルで続く
- 追加4モデル（`train_multi.py`）: 合わないモデルだけ学習しない（先週のモデルのまま）。
  ステップは失敗で返す。探索が打ち切られて一部のモデルしか探索し直せなかった週は
  こうなる

205列は153列より探索が重い。実験39（Actions、205列）の実測で LightGBM 11分 /
XGBoost 25分 / CatBoost 22分。`logit` は153列で70分だったので、それより延びる。

引き換えに、特徴量も母集団も変えていないのに**パラメータが週ごとに動く**。
予測が変わったときに「相場が変わった」のか「パラメータが変わった」のかを
切り分けられなくなるのが唯一の副作用なので、`research/lgbm_params.json` の
差分を毎週の実行要約に出してある。何が動いたかは毎週その場で見える。
ファイル自体も毎週コミットされるので、git の履歴で遡れる。

## 母集団（何を採点しているか）

その日に**78週高値を更新した銘柄だけ**が候補になる（`build_dataset.py` の
`POPULATION = "breakout"`）。直前20営業日に更新が無い日だけを「新規のブレイク」と
みなすので、同じ上昇局面で高値更新が続いても1件にまとまる。1日あたり数件。

その日の引け後に採点し、翌営業日に買うかを判断するための出力。

### ETF・ETN・REIT は母集団から外した（2026-09-17）

**結論を先に**: `mkt_code == 109`（市場区分「その他」= ETF / ETN / REIT /
インフラファンド）は母集団から外した。設定は `build_dataset.py` の
`EXCLUDE_MKT_CODES`。判断の根拠と、効き始める時点は
下の「測り直し（2026-09-17）」の節の末尾に書いた。

以下は 2026-09-11 時点の記録で、**このときは放置する判断だった**。
なぜ判断が変わったかが残るように、当時の内容はそのまま置いてある。

市場区分によるフィルタは掛けていない（`mkt_code` は特徴量として使うだけ）。
そのため上場投信の類も母集団に入り、**スコア上位5%の41.7%を占める**。
母集団では7.6%しかないので5.5倍の過剰代表。不具合ではない。

| | 母集団 | 上位5% | 倍率 |
|---|---:|---:|---:|
| ETF等（`mkt_code == 109`）の比率 | 7.6% | 41.7% | 5.5x |
| ボラ中央値 | 1.84% | 0.99% | — |

**機構**: ボラ正規化ラベルのしきい値は `1.2 × σ × √60` なので、低ボラほど
バーが低い（ボラ0.88%なら必要上昇8.2%、6.31%なら58.7%）。ETF は分散された
バスケットで構造的に低ボラ（中央値0.97% / 株式2.04%）なため、正例になりやすい。
株式だけに限ってもボラ十分位で正例率が単調に 31.2% -> 8.3% と落ちる。

ランダムウォークなら到達確率はボラによらず一定のはずで、この勾配が出るのは
**ボラの平均回帰**が効いているためと考えられる（直近20日が高ボラな銘柄は
将来ボラが下がりやすくバーに届かない、低ボラ銘柄は逆）。これは未検証の仮説。

**放置してよい理由**: 実収益（`ref_end`、ラベル非依存）で見ると優位性は
ETF 由来ではない。外してもほぼ変わらない。

| | 母集団 | 上位5% | 差 |
|---|---:|---:|---:|
| ETF込み（現行） | +3.41% | +5.86% | +2.45pt |
| 株式のみ | +3.36% | +5.66% [+4.40, +6.89] | +2.30pt |

上位5%の中でも株式部分（+6.71%）のほうが ETF 部分（+4.67%）より良い。
実収益はボラ十分位ともほぼ無関係（十分位0で+3.39%、十分位9で+2.24%、単調ですらない）。

> **2026-09-17 追記: 上の「株式部分のほうが良い」は、いまの物差しでは逆転する。**
> 当時は全期間プールの上位5%・終値買い・60営業日（`ref_end`）で測っていた。
> 運用の物差し（翌営業日の寄り買い・40営業日・しきい値は過去の窓だけから決める）
> で測り直した結果は下の節。

### 測り直し（2026-09-17 / `research/exp/e17_etf.py`）

物差しを運用に合わせ、種3個の確率平均で測り直した。

**上位10%に選ばれた2,000件の内訳**（現行＝ETF込みで学習・採点）

| | 件数 | 構成比 | 実収益 中央 | 平均 | 勝率 | 25%分位 |
|---|---:|---:|---:|---:|---:|---:|
| ETF等 | 502 | 25.1% | **+2.79%** | +2.38% | **67.7%** | **-1.73%** |
| 株式等 | 1,498 | 74.9% | +2.24% | **+3.58%** | 59.7% | -3.62% |
| 全体 | 2,000 | 100% | +2.52% | +3.28% | 61.7% | -3.18% |

**ETF のほうが中央値も勝率も高く、下振れも浅い。** 株式のほうが平均は高い
（裾が厚い）。

この節を最初に書いたとき、「安定した少額の利益を狙うなら ETF は外すべき
ではない」と結論した。**これは前提を取り違えていた**。「安定した少額の利益」
は株式の運用についての話で、この仕組み全体の目標ではない。この仕組みは
値幅を取りにいくものなので、中央値が高く平均が低い ETF は噛み合わない。
実測の数字はそのまま（上の表は正しい）で、そこから引いた結論だけが誤りだった。

**学習から外しても効果は無い**（評価母集団を揃えた比較）

| 条件 | 窓平均 | 標準誤差 | 勝ち窓 | 最悪の窓 |
|---|---:|---:|---:|---:|
| A  学習=全部 / 評価=全部（現行） | +0.80pt | 0.32 | 7/9 | -0.73pt |
| A' 学習=全部 / 評価=株式のみ | +1.17pt | 0.26 | 9/9 | +0.17pt |
| B  学習=株式 / 評価=株式のみ | +1.28pt | 0.33 | 9/9 | +0.22pt |

A' と B の差は **+0.11pt / z=0.27 で差なし**。つまり **ETF を学習データから
外す意味は無い**（外すなら候補から落とすだけでよく、再学習は不要）。

A と A' の差（+0.37pt / z=0.90）も足切りを越えないが、勝ち窓が 7/9 → 9/9、
最悪の窓が -0.73pt → +0.17pt に変わる。ただし勝率は 61.7% → 57.8% に**落ちる**。
安定性を取るか、負ける窓を消すかのトレードオフで、平均リターンはほぼ同じ
（+3.28% → +3.22%）。

**上位10%に占める ETF 比率は窓ごとに 5.8%〜57.8% と大きく振れる。**
買う対象の構成が週によって入れ替わるので、そこが気になるなら外す理由になる。

**読むときの注意**: 正例率はボラで大きく歪むが実収益は歪まない。つまり画面と
スプレッドシートの**較正確率・帯の正例率は、低ボラ銘柄で系統的に楽観側にずれる**。
帯の実収益（`bandEndMedian`）のほうが素直に読める。

**外した**（2026-09-17）。母集団の定義そのものから落とす形にした。
`research/build_dataset.py` の `EXCLUDE_MKT_CODES`（既定 `(109,)`）で、
`mkt_code` を結合した直後に1箇所で切っている。学習データ・OOF（スコア帯と
較正表の元）・日次予測の候補が同じ1行で揃うので、母集団が食い違わない。

A' と B に差が無い以上、学習から外すこと自体に効果は期待していない
（期待しているのは A→A'、つまり候補から外すぶん）。それでも1箇所で切るのは、
帯の正例率や較正確率を**候補と同じ母集団**で作り直すためで、
学習だけ ETF 込みのまま残すと帯と候補がずれる。

効き始める時点は非対称になる:

| | 変わる時点 |
|---|---|
| 日次予測の候補から ETF が消える | このコミットの次の Predict Breakouts から |
| スコア帯・較正確率が株式だけの母集団になる | 次の Retrain Weekly（日曜）から |
| 「開示からの日数」（`days_since_disc` / `days_since_fy`）が特徴量に入る（2026-09-22 に採用。`docs/MODEL_DISCLOSURE_TIMING.md`） | 次の Retrain Weekly（日曜）から 153列。日次予測は meta.json の特徴量一覧で採点するので、それまでは旧モデル（151列）のまま |

戻したいときは `EXCLUDE_MKT_CODES = ()`（または環境変数
`SWEEP_EXCLUDE_MKT_CODES=none`）。実際に効いた設定は
`dataset_meta.json` の `excludeMktCodes` に残る。
母集団は 22,887 → 21,138件（-1,749件 / -7.6%）、
正例率は 20.85% → 19.93% になった。

**過去ぶんの見分け方**: 除外は今後の予測にだけ効くので、
スプレッドシートに既に入っている ETF の行は残る。業種が「その他」で
時価総額が空欄の行がそれ。

## スプレッドシートの列

このパイプラインが書くのは左側の列だけで、**右側の記入欄には一切書き込まない**。

- 書く（追記時に1度）: 予測日 / コード / 銘柄名 / 業種 / 順位 / 候補数 / スコア / 帯 /
  較正確率% / 帯の正例率% / 帯の実収益% / 帯の勝率% / 必要上昇率% / 予測時株価 /
  時価総額 / 売買代金 / 日次ボラ% / 20日リターン% / 地合い寄与 / 銘柄固有寄与 / PER / PBR
- 書く（モデル別・追記時に1度）: LGB% / XGB% / CAT% / LR% / NN% /
  LGBスコア / XGBスコア / CATスコア / LRスコア / NNスコア / 一致(上位10%)
- 書く（値が決まったら1度）: 翌営業日始値
- 毎回更新: 現在値 / 騰落率% / 経過営業日
- **触らない（記入欄）**: 建値 / 株数 / 手仕舞い日 / 手仕舞い値 / 損益 / メモ

**翌営業日始値**（2026-09-25 に追加）は、予測日の次の営業日の始値。運用の規則は
「翌営業日の寄りで買う」なので、収益はこの値を基準に数える。予測時株価・現在値と
同じく分割調整なしの、その日に実際に付いた値。予測した夜にはまだ無く、次の営業日の
日足を取り込んだ夜に入る（連休をまたぐときは連休明けの始値）。寄り付かなかった日は
空のまま。一度入った値は書き直さない。既存のシートでは見出しの右端に足されるので、
見やすい位置へ手で動かしてよい（名前は変えないこと）。なお「騰落率%」は今も
予測時株価（予測日の終値）が基準で、翌営業日始値からの値ではない。

列は**見出しの名前で探す**。途中に自分用の列を挿しても壊れない。
行は追記のみで、既存行を作り直さない（作り直すと手入力が消える）。

### モデル別の列の読み方

2種類ある。

| 列 | 中身 | 使い方 |
| --- | --- | --- |
| `LGB%` など | そのモデル自身の**過去スコア分布での位置**（0〜100）。画面の棒グラフと同じ値 | **モデルをまたいで比べられるのはこちらだけ** |
| `LGBスコア` など | モデルが出した**生の値** | 同じモデルの中で日をまたいで追う／自分でしきい値を引き直す |

**生スコアはモデル間で大小を比べてはいけない。** 実例（2026-09-11 の1699）。

| | LGB | XGB | CAT | LR | NN |
| --- | ---: | ---: | ---: | ---: | ---: |
| 位置% | 90.3 | 89.4 | 94.4 | 54.4 | 84.3 |
| 生スコア | 0.535 | 0.474 | 0.615 | 0.500 | 0.294 |

NN の生スコア 0.294 は LR の 0.500 より小さいが、**位置は NN 84.3 > LR 54.4**。
学習器ごとに確率の出方が違うためで、生スコアの大小には意味がない。

位置だけだと後から別のしきい値で切り直せない（順位に潰れている）ので、
生スコアも併せて残してある。

既存の `スコア` 列は基準モデル（LightGBM）の生スコアで、`LGBスコア` と同じ値。
運用開始時から入っている列なので、過去行との連続性のために残してある。

`一致(上位10%)` は上位10%と見ているモデルの数（例 `3/5`）。独立した判定の
数え上げで、スコアを混ぜた値ではない。**平均は出していない** — 混ぜた数字を
1つ出すと、呼び名が何であれアンサンブルになるため。

`順位 / 帯 / スコア / 較正確率%` はすべて**基準モデル（LightGBM）**のもので、
`LGB%` と同じモデルを指す。モデル別の列は隣に並べる参考値で、順位には効かない。

読むときの注意（実測・`docs/MODEL_LINEUP.md`）。

- 木3つ（LGB / XGB / CAT）は互いに相関 0.80〜0.89、上位10%の重複 50〜58%。
  **揃って高くても独立した3票ではない**
- 木以外2つ（LR / NN）は互いに 0.823。塊をまたぐと 0.63〜0.71 に落ちる
- **塊をまたいで揃ったとき**だけ、見方の違うモデルが同じ結論に達したと読める

### 列が増えたとき

このパイプラインが書く列が増えたら、**見出し行の右端に自動で足される**
（`ensure_columns`）。途中に挿し込まないので、既存セルはずれず、記入欄の
中身は動かない。直近5営業日ぶんの既存行には、空のままのセルだけ埋める
（すでに値があるセルは手で直した可能性があるので触らない）。

並び順が気になるときは、**見出しを手でドラッグして動かしてよい**。
列は名前で探しているので、どこにあっても正しく書き込まれる
（名前そのものを変えると、その列は書き込み対象から外れる）。

## 営業日カレンダー（2026-09-22 に入れた）

### 何が起きたか

2026-09-21（敬老の日）〜09-23（秋分の日）の3連休で、日次予測が赤で落ちた。

```
[freshness] 日次バーの最終日 2026-09-18 / 基準日 2026-09-22 / 遅れ 2営業日（許容 1）
[fatal] 生データが古すぎます
```

落ちた経路は2つある。

1. **鮮度チェックが遅れを平日で数えていた。** `np.busday_count` は祝日を
   知らないので、連休では遅れを多く見積もる。3連休だと許容の1を超える
2. **営業日ゲートが manifest の鮮度（12時間以内）を条件にしていた。**
   連休2日目は**その日の取り込みがまだ走っていない**ので使えない。
   実測で manifest は18時間前だった

### どう直したか

**`/markets/calendar` の応答を保存するようにした。** 取り込み
（`jq_bulk.trading_days`）は元からこのエンドポイントを叩いて営業日を
決めていた。叩いているのに捨てていただけ。

| 部品 | 役割 |
|---|---|
| `research/trading_calendar.py` | 保存・読み出しと、営業日の数え方 |
| `research/_data/calendar.parquet` | `Date` と `HolDiv`。Release にも載る |
| `research/check_freshness.py` | カレンダーで数える。無ければ平日（厳しい側） |
| `research/trading_day_gate.py` | カレンダーで判定。範囲外なら manifest に落ちる |

**先の日まで取っておく**（`CALENDAR_LOOKAHEAD_DAYS = 45`）。下流は「今日」が
カレンダーの範囲に入っていないと使えず、取り込みが当日まだ走っていない
時刻に予測が動くことがあるため。取りに行く対象は従来どおり end まで。

### カレンダーを言い訳にしないための決め事

元のコードには「ここで祝日カレンダーを持ち込むと、更新が止まったときに
『祝日だから』と自分で言い訳する余地を作ってしまう」というコメントがあった。
**その懸念は自分で推測する場合の話**で、いまは取引所が公表した事実を読む。
それでも緩まないように、こう決めてある。

- **カレンダーが対象日を覆っていないときは使わない。** 平日で数える側に倒す
- **カレンダーが「営業日だ」と言っている日にデータが無ければ、遅れとして
  数える。** 祝日を持ち出せるのは、取引所が非営業日だと言った日だけ
- ゲートは、保存データが**カレンダー上の直近の営業日に届いている**ことまで
  確かめてから飛ばす。取り込みが壊れていれば休場日でも飛ばさない
- ファイルが無くても壊れていても例外を投げない。ここが新しい障害の
  入口になってはいけない

### 実測（2026-09-22 の条件を再現）

| 基準日 | カレンダーあり | カレンダーなし（従来） |
|---|---|---|
| 2026-09-22（国民の休日） | 遅れ1 → **OK**、ゲートが飛ばす | 遅れ2 → **落ちる** |
| 2026-09-23（秋分の日） | 遅れ1 → OK | 遅れ3 → 落ちる |
| 2026-09-24（営業日・当日ぶん未取得） | 遅れ1 → OK | 遅れ4 → 落ちる |
| 2026-09-25（09-24 を取りこぼし） | 遅れ2 → **落ちる**（正しい） | 遅れ5 → 落ちる |

いちばん下が肝で、**本物の取りこぼしは今までどおり落ちる**。

テストは `tests/test_trading_calendar.py`（28件）。

### 予測済みの日を予測し直さない（2026-09-24 に直した）

**ゲートは壁時計の日付ではなく「まだ予測していない日足があるか」で決める。**
それまでは「今日（日本時間）が営業日か」で決めていたため、次の2回、予測済みの 9/18 を
新しいモデル（9/20 学習）で予測し直し、追跡記録に当時は選んでいない銘柄（日本ナレッジ）を足した。

| 日時（JST） | 起動 | 起きたこと |
|---|---|---|
| 9/24 0:09 | 手動（休場日の確認のつもり） | 日本時間の翌日（営業日）と判定され最後まで走った（run 35879476135）。500e3c6 で取り除いた |
| 9/24 3:24 | **自動**。休場日 9/23 の取り込みが日付をまたいで終わり、連鎖した予測が走った | 同じ1件が再び入った（1f18614）。2026-09-24 に取り除いた |

2回目は手動の注意書きでは防げない形だった。直したこと:

1. **ゲート**（`research/trading_day_gate.py`）: 保存データの最終バー日が、公開済みの
   `predictions.json` の `asOf` より新しいときだけ予測する。新しくなければ飛ばす。
   営業日の 18:00 JST（取り込みの待ちの締切）を過ぎてもその日の日足が無ければ、
   飛ばしたうえで**最後に赤にする**（`Fail if bars are missing`）。休場日でも未予測の日足が
   あれば予測する。意図して予測し直すときは `workflow_dispatch` の `force`
2. **追跡記録**（`predict_daily.update_history`）: その日の記録が1件でもあれば後から足さない
   （最初の予測で凍結）。現在値などの追跡列は更新を続ける
3. **経過日数**: 追跡記録と台帳の「経過営業日」を、平日ではなく取引所の営業日で数える
   （連休3日を経過日に数えていた）
4. テストで固定した（`tests/test_trading_calendar.py` の `TestNoRepredict`、
   `tests/test_prediction_record.py`）。CI は `tests/` の全部を回すようにした（下記）

台帳（スプレッドシート）は全候補を1行ずつ持ち、モデル別の列は空のセルにしか書かないので、
予測し直しで当時の値が書き換わることは無い（`tests/test_sheets.py` が固定している）。

### CI が回していなかったテスト（2026-09-24 に直した）

CI の研究コードのテストは、回すファイルを1本ずつ列挙していた。14本のうち6本しか回っておらず、
営業日ゲート・特徴量・損切りのテストは CI で一度も走っていなかった。さらに4本はファイルの途中で
`unittest.main()` を呼んでいたため、スクリプトとして実行すると後ろのクラスが黙って飛ばされていた
（`test_model.py` は 120本中106本だけ）。`python3 -m unittest discover -s tests` に替え、
全部（2026-09-24 時点で620本）を回す。新しいテストを足しても CI を書き換える必要は無い。

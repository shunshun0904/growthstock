# 運用と保存先

予測結果・モデル・生データがどこに置かれ、どの頻度で更新されるか。

## 置き場と役割

| | 中身 | 置き場 | 更新 | なぜそこか |
|---|---|---|---|---|

| 画面用の追跡 | `public/data/prediction_history.json`（上位5件/日・400日で削除） | git | 平日夜 | 画面に出すぶんだけ。**長期の台帳ではない** |

## 動く順番

```
平日 18:40 JST  Update Data Store    その日のデータ（四本値・指数・空売り比率・大量保有・
                                     決算）が出そろった後に起動する
                                     → J-Quants から差分取得 → Release へ
      ↓ 完了で起動
                Predict Breakouts    Release からモデルと生データを取得
                                     → 鮮度チェック（1営業日より古ければ停止）
                                     → 予測データセット構築 → 採点
                                     → 画面の候補（最大120銘柄）の詳細を取得（stocks.json）
                                     → スプレッドシートへ追記
                                     → コミット → Pages 再デプロイ
      ↓ 完了で起動
                Update Holdings Sheet 報告した取引を「取引の記録」タブに写し、売りのルールで
                                     損益の推移を「保有の推移」タブに作り直す（日付ごとの
                                     表とグラフ）。予測ログの行を赤（保有中）・青（売却済み）に塗る

平日 13:10 JST  Fetch JSF            日証金の前営業日の確報（daily）と、銘柄ごとの
土日 10:20 JST                       過去3年の続き（history）を Release（data-jsf）へ。
                                     土日は history だけ

毎日 10:10 JST  Fetch EDINET DB      EDINET DB から年次財務を 85社ぶん取って
                                     Release へ（1社1リクエスト。月 850 で止まる）

日曜 09:10 JST  Retrain Weekly       J-Quants から差分取得（日曜は取り込みが
                                     走らないので自分で取りに行く）
                                     → 鮮度チェック（2営業日より古ければ停止）
                                     → Release へ書き戻し → 学習
                                     → モデルを Release へ、meta.json を git へ

土曜 10:40 JST  Check Data Store     保存データ（data-raw）を API の応答と突き合わせる
                                     （種別ごとに数日ぶんを叩き直す）

月〜土 07:40 JST 朝の確認（Routine だけ） 前日の取り込み・予測・日証金・EDINET DB の run の
                                     結論を確かめる。取り込みが無ければ Update Data Store を
                                     起動し直す。月曜は日曜の学習と土曜の検査を見る

手動            Refresh Stock Details  画面の銘柄データ（stocks.json）だけを作り直す。
                                     予測はしない。対象は公開中の predictions.json から
                                     日次予測と同じ規則で選ぶ → 株価推移の期間を確かめる
                                     → コミット → Pages 再デプロイ
```

`Refresh Stock Details` は、取得スクリプト（`scripts/jquants_data_fetcher.py`）の作りを
変えたときに、次の日次予測を待たずに画面へ出すためのもの（2026-09-26、株価推移と
タイムラインを直近1年から目的変数と同じ78週にしたときに足した）。ふだんは使わない。

**データを積むワークフロー（取得・予測・取り直し）の後の Pages 再デプロイは、公開ブランチの
先頭を載せる。** 2026-09-26 までは起動元が走り始めたときのコミットを載せていたので、
その日の予測が画面に出るのは、次に誰かが push したときだった（`.github/workflows/deploy-pages.yml`
の注記。`tests/test_refresh_details.py` で、`public/data` を積むワークフローが全部デプロイに
繋がっていることと合わせて確かめる）。

### 起動のしかた（2026-10-05 から Claude の Routine。GitHub の cron はやめた）

**ワークフローに予約の起動（`schedule:` の cron）は無い。** 2026-10-05 に全部外した。
代わりに Claude の Routine（claude.ai の「ルーチン」。時刻は JST で指定できる）が、決めた時刻に
`workflow_dispatch` で起動する。起動する側が変わっただけで、ワークフローの中身は同じ。

| Routine | 起動 (JST) | 起動するワークフロー | 入力 | Routine の ID |
|---|---|---|---|---|
| 取り込み | 平日 18:40（10/7 までは 16:10） | Update Data Store | `wait=yes`（18:40 にはふつう出ているので、1回確かめて進む） | `trig_01M9v8tkNfW2K7W5cNcnfyCa` |
| 日証金（平日） | 平日 13:10 | Fetch JSF | `mode=both` | `trig_0123KKDZgbRthzbicWPBnr1k` |
| 日証金（土日） | 土日 10:20 | Fetch JSF | `mode=history` | `trig_01VF9LEPhar2yRaZSzpfZmsX` |
| EDINET DB | 毎日 10:10 | Fetch EDINET DB | 既定（85社・対応表は auto） | `trig_018mSPXUBa4PBFsHpK5BzNpK` |
| 週次学習 | 日曜 09:10 | Retrain Weekly | `tune=yes` | `trig_01MQSVtn55Vmy7HmKjs9mJ6p` |

Routine はすべて、この運用を続けている Claude のセッション（`session_01HavkjgQwRz5mTV8cGj4KJp`、
claude.ai の「jquants APIブラウザアプリ」）に届き、そのセッションが `curl` で workflow_dispatch を送る
（`Authorization: Bearer $GITHUB_TOKEN`。このセッションにはリポジトリの GitHub 認証がある）。起動後に run が
現れたことと完了を確かめ、run の ID と結論、件数だけを報告する。Secrets や銘柄ごとのデータの値は出さない。
失敗したときは落ちた step を読んで、一時的な原因（ネットワーク・GitHub の 5xx・Release の入出力）なら
1回だけ失敗した job を再実行し、それ以外は再実行せずに報告する。

**新しいセッションで動かす形（起動のたびに別セッション）は使えなかった。** 2026-10-05 に試した
（ドライランを4回）ところ、Routine が作る新しいセッションにはリポジトリが無く、GitHub API は 403
（"GitHub access to this repository is not enabled for this session"）、GitHub の MCP ツールも無い。
raw.githubusercontent.com は読める。そのため Routine は既存のセッションに紐づけてある。
**このセッションをアーカイブすると Routine は止まる**。そのときは、リポジトリの GitHub 認証を持つセッション
から Routine を作り直すか、claude.ai の Routine の画面でリポジトリを付けて作り直す。

Predict Breakouts は Routine からは起動しない。取り込みの完了で `workflow_run` が繋ぐ（上の図）。
Routine が起動した run は、Actions の一覧では `workflow_dispatch` として見える（以前の予約の起動は
`schedule`）。Routine が走った記録（起動した run の ID と結論、件数）は claude.ai のそのセッションに残る。

なぜ cron をやめたか: GitHub の予約の起動は実測で +4時間01分〜+7時間19分遅れ（下の
「起動時刻を 21:30 から 16:05 に前倒しした」の表）、10/5（月）は 07:05 UTC の予約が 14:33 UTC
（23:33 JST）になっても来なかった（運用者の了承で手動起動。run 37325682385）。遅れが翌日にかかると、
翌日の取り込みが2日ぶんを取って予測は最新の日だけを記録するので、その日の予測が抜ける。
時刻を指定して起動すれば、公開時刻は起動の時刻で決まる。最初は 16:10 に起動したが、その日の
データが予測に間に合わない種別があったので、10/8 から 18:40 にした（下の「取り込みを 18:40 に移した」）。
見込みは 18:50 ごろの公開（取り込み 4〜5分・予測 5〜6分は 10/5〜10/7 の実測）。

学習は探索込みで3〜5時間かかるので、日曜 09:10 に始めて昼過ぎに終わる見込み。

#### 取り込みを 18:40 に移した（2026-10-07、運用者の了承。10/8 から）

**16:10 の起動では、その日の公表ぶんの一部が予測に間に合わない。** 10/7 の学習と予測の一致チェック
（予測 run 37586277747）で `short_ratio`・`short_ratio_20` が 8行（13.1%、1日 = 10/6 の候補の全件）、
`lvs_ratio`・`lvs_ratio_chg` が 2行（3.3%）食い違った。10/7 の取り込み（run 37585874840、16:12 起動）の
ログでは、空売り比率は 10/7 が0件で、10/6 の 34行がこの日に初めて入った（決算も 10/6 の 15行がこの日に
入った）。つまり 10/6 の予測は 10/5 の空売り比率で計算され、後から作り直した学習の行には 10/6 の値が入る。
空売り比率は 16:30 ごろ、大量保有報告書は 17:31 まで増え、決算は 18:00 ごろに出る（`docs/DATA_TIMING.md` の表）。
予約の起動のころは 16:05 の指定でも実際は 21〜23時に走っていたので表に出なかった。

- 取り込みの Routine を 18:40 に移した（決算の 18:00 ごろに余裕を足した）。モデルと特徴量は変えていない
- 16:10 に予測した 10/6・10/7 の行は、一致チェックで比べない（`research/check_train_serve.py` の
  `EARLY_RUN_DAYS`）。控えは 400日残るので、外さないとずっと許容を超える
- 週次の信用残・投資部門別の公表時刻はまだ測っていない。18:40 でも間に合わない列があれば、
  一致チェックに出る

- **止めたいとき**: claude.ai で Routine を無効にする（ワークフローは触らない）。
- **手で起動したいとき**: Actions の画面の `Run workflow` で同じ入力を渡せば、Routine と同じになる。
  Routine の時刻（上の表）と重ねない。
- **戻したいとき**: 各ワークフローの `on:` に `schedule:` を戻す。外した cron（UTC）は
  Update Data Store `5 7 * * 1-5`、Predict Breakouts `0 14 * * 1-5`（保険）、Fetch JSF `5 4 * * 1-5` と
  `5 4 * * 0,6`、Fetch EDINET DB `5 1 * * *`、Retrain Weekly `5 0 * * 0`、Check Data Store `5 1 * * 6`。
  `github.event_name == 'schedule'` で分けていた条件（取り込みの待ちは `inputs.wait`、日証金の
  daily/history は `inputs.mode`、学習の探索は `inputs.tune` に置き換えた）も戻す。
  `tests/test_refresh_details.py` の `TestWorkflows` が「cron が無いこと」を固定しているので、戻すときは
  テストも直す。

鮮度チェックを入れてあるのは、取り込みが失敗した日に黙って昨日と同じ候補を出したり、
先週のデータで学習し直したりするほうが害が大きいため。気づけないことが一番よくない。

### 保有の推移と取引の記録（スプレッドシートの別タブ。2026-10-08 から）

運用者がチャットで「買った（ことにした）」「売った（ことにした）」を報告し、セッションがそれを
シートに反映する。損益の推移は、下の売りのルールで描く（運用者の依頼。2026-10-08）。

```
チャットで報告   → セッションが research/trades_inbox.py add で暗号化して
                    research/trades_inbox.jsonl に1行足し、コミット・プッシュ
                    （すぐ反映したいときは Update Holdings Sheet を手で起動する）
毎晩の予測のあと → Update Holdings Sheet（.github/workflows/holdings.yml、research/holdings_sheet.py）が
                    復号して「取引の記録」タブに写し（id で重複を除いて足すだけ）、
                    「保有の推移」タブを作り直し、予測ログの行を塗る
```

**なぜ暗号化するか。** リポジトリと Actions のログは公開。シートに書けるのはサービスアカウント
（Actions の Secrets）だけで、チャットのセッションからは書けない。そこで、サービスアカウントの鍵の
公開側（`research/trades_pubkey.pem`）で暗号化した行をリポジトリに置き、Actions が秘密鍵で戻す。
公開されるのは、行を足した日時と行数だけ（id は無作為の文字列）。行ごとに使い捨ての AES-256-GCM の
鍵で中身を暗号化し、その鍵を RSA-OAEP(SHA-256) で包む。

報告の足し方（セッションが打つ。出力は id の先頭だけで、銘柄や値段は出さない）:

```
python3 research/trades_inbox.py add --action buy  --code 6912 --pick-date 2026-09-24 \
    [--date 買った日] [--price 買値] [--shares 株数]
python3 research/trades_inbox.py add --action sell --code 6912 --date 2026-10-20 [--price 売値]
python3 research/trades_inbox.py add --action cancel --ref <取り消す行の id の先頭 8 文字以上>
```

- 買い: 予測日（予測ログの行を見つけるのに使う）か買った日のどちらかが要る。買った日が無ければ予測日の
  次の営業日の寄り付きで買ったことにする。値段が無ければその日の始値、株数が無ければ 100 株
- 売り: 売った日が要る。値段が無ければその日の終値。同じコードで、売った日までに買った保有のうち
  いちばん新しいものを、まるごと売ったことにする
- 取消: 取引の記録タブの id 列（先頭 8 文字以上）で指す。間違えた報告はこれで消す（タブの行を消しても、
  受け皿に残っているので次の晩にまた足される）。値の訂正は、取り消して出し直すか、取引の記録タブの
  セルを手で直す（足したあとの行は上書きしないので、手で直した値が使われる）

**売りのルール**（運用者の決定。2026-10-08）

- 買った日（寄り付きで買う）を1日目として 20 営業日以内に、日中の高値が 買値×1.10 に届いたら、
  その日に 買値×1.10 で売ったことにする（指値を置いておく想定）
- 届かなければ 20 日目の終値で売る。終値が買値を下回っていたら売らずに持ち越し、売りの報告があるまで
  持つ（持ち越したあとは、ルールでは売らない）
- 売りの報告はルールより優先する（ルールで売ったことになっていても、報告の日・値段に置き換える）
- 営業日は取引所のカレンダーで数える。買う日の日足が保存データに無ければ、埋めずに待つ（買い待ち）
- ルールで売ったものも、報告の売りと同じく売却済みとして確定する

**予測ログの色と列**

- 取引の記録がある行だけを塗る。保有中（持ち越し・買い待ちを含む）は**赤**、売却済みは**青**（#4a86e8。2026-10-09 までの黄色は「文字が見えない」ので変えた）、
  取り消した買いの行は塗りを外す。ほかの行の色には触らない
- その行の「建値」「株数」「手仕舞い日」「手仕舞い値」「損益」を毎晩書き直す（取り消した行は空にする）。
  この5列を手で直しても次の晩に戻るので、直すときは取引の記録タブで直す
- 以前の「行を赤く塗ると保有とみなす」決め方は 2026-10-08 にやめた（手で赤く塗っても読まない）

**保有の推移タブ**（毎晩まるごと作り直す。このタブに手で書いた内容は消える）

- 銘柄ごとの表（予測日・買った日・建値・株数・+10%の値・20日目・20日目までの高値とその日・売った日・
  売値・売りの理由・最新日・最新終値・損益・状態）と、合計・うち確定（売却済み）・うち含み（保有中）。
  「+10%の値」は売りの指値（建値×1.10）、「20日目までの高値」はルールで見た日中の高値の最大（売った日まで）
  で、保有中のものが +10% にどこまで近づいたかが分かる
- 日付ごとの表（合計損益・合計損益%・保有数・銘柄ごとの損益）。銘柄の列は持っている間だけ（売った日
  まで）。合計には、売ったあとも確定した損益が残る
- 日々の値は終値。買ったあとに分割・併合があっても、買った日の株の単位に戻して数える
  （調整後の値 ÷ 買った日の調整の比）
- 合計損益% は、合計損益 ÷ それまでに買った建値の総額
- グラフは日付ごとの損益（円）の折れ線（軸は1本）。合計は淡い青の太い帯で、その上に保有中と、売って
  から 20 営業日以内の銘柄の線を重ねる。色は買った順に、グラフに出る期間の重なる銘柄どうしで違う色に
  する（あとから買った銘柄で、先の銘柄の色は変わらない）
- 公開ログには件数と最新日だけを出す（銘柄名・株価・損益の値は出さない）。報告が合わなかったときは
  種類だけを出す（「売りに合う買いが無い」など）

**サービスアカウントの鍵を作り直したら**、Update Holdings Sheet を mode=pubkey で手で起動し、ログに
出る公開鍵を `research/trades_pubkey.pem` に置き直す。古い鍵で暗号化した行は戻せなくなる（ログの
「復号できない」に数える）が、取り込み済みの取引は取引の記録タブに残っているので失われない。

### 休場日はどうなるか

Routine は平日に起動する（祝日カレンダーは持たない）ので、祝日でもワークフローは動く。

| | 休場日の挙動 |
|---|---|
| Update Data Store | 待ちは締切で諦めて **exit 0**。営業日カレンダーに祝日は入らないので取得対象が無く、**成功**で終わる |
| Predict Breakouts | **営業日ゲートで飛ばす**（下記）。緑のまま「本日は非営業日」で終わる |
| 画面 | 前営業日の内容のまま据え置き |
| 台帳 | 追記なし（`(予測日, コード)` で重複排除） |

**鮮度チェックだけでは連休をさばけない。** 遅れを**平日**で数えており
（祝日カレンダーは意図的に持ち込んでいない。持ち込むと「更新が止まったのに
祝日だからと自分で言い訳する」余地ができる）、日次予測の許容は1営業日なので、
3連休では2日目・3日目が「遅れ2〜3営業日」で止まる。止まること自体は正しいが、
**正常な休場と本物の取り込み障害が同じ赤い×になる**。連休のたびに赤を見れば、
本物を見逃す訓練になってしまう。

そこで、**営業日かどうかを推測せずに受け取る**。

```
Update Data Store   J-Quants の営業日カレンダーを引く（ここだけが引いている）
                    → manifest.json の calendar に事実として書き残す
                       {"asOfJst": "2026-09-21", "isTradingDay": false,
                        "lastTradingDay": "2026-09-18"}
      ↓ Release 経由
Predict Breakouts   research/trading_day_gate.py がそれを読むだけ
                    → 非営業日なら以降のステップを飛ばして緑で終わる
```

予測側にカレンダーを持ち込むのではなく、既に知っている側から渡す形にしてある。
予測側が自分で「祝日だから」と言い訳できる余地は作っていない。

**飛ばすのは3条件がすべて揃ったときだけ。**

1. `calendar.isTradingDay` が**明示的に false**（`null` や欠損は飛ばさない）
2. 保存データの最終バー日 == `calendar.lastTradingDay`
   —— **ここが肝**。取り込みが壊れていれば保存データは直近の営業日に届いて
   いないので、休場日であっても飛ばさず、鮮度チェックで落とす
3. manifest が12時間以内に更新されている（取り込みが今日走ったこと）

どれか1つでも欠ければ通常どおり進む。**飛ばす側には倒さない。**
判断できない事情（manifest が読めない、バーが無い）もすべて「進む」に倒し、
ゲート自体は必ず exit 0 で返す。止めるかどうかは鮮度チェックの仕事のまま。

例：2026-09-21〜23（敬老の日・国民の休日・秋分の日）

| 日 | Update Data Store | Predict Breakouts |
|---|---|---|
| 9/21(月) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/22(火) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/23(水) | ✅ 取得なし | 🛌 ゲートで飛ばす（緑） |
| 9/24(木) | ✅ 09-24 を取得 | ✅ 新しい候補 |

23:11 JST）。予測（`Predict Breakouts`）は workflow_run で続き（9/28 は 23:14 開始・23:22 公開）、
予測するかは「まだ予測していない日足があるか」で決めるので、0時を過ぎても正しい日の予測になる。
あとから予約の起動が来ても、同じ取り込みは順番待ちになり、予測は「予測済み」で飛ばされる。
起動が来ないまま翌日の取り込みが走ると、2日ぶんの日足を取っても予測は最新の日だけを記録する
（`predict_daily.py` の `latest`）ので、その日の予測が抜ける。手動起動はそれを防ぐため。

**0時を過ぎた予約の起動は、前日のデータを取らずに5時間半待って打ち切られていた（2026-10-02 に修正）。**
取り込みの前の待ち（`research/wait_for_data.py`）は「今日（JST の暦日）」の日足が出るのを
18:00 JST まで待つ。0時を過ぎて起動すると「今日」は翌日になり、その日足は夕方まで出ないので、
ジョブの上限（330分）まで待って打ち切られていた（2026-09-28 の予約の起動 run 36442731228）。
前日の日足は取られず、その夜に手動で起動していなければ、その日の予測が抜ける。
いまは、大引け（15:30 JST）より前に起動したときは待たずに進む。取り込みの終わりの日は
`date -u` の日（0時〜9時 JST なら前日）なので、前の営業日までを取る。予測は「まだ予測していない
日足があるか」で決めるので、0時過ぎに前日の予測が出る（鮮度の検査は UTC の日付で数えるので
通る）。`tests/test_fetcher.py` の `TestWaitForData` で固定。

**手動で起動するときは、予約の起動との重なりに注意する。** `Predict Breakouts` は
`cancel-in-progress: true` なので、二つ目の取り込みが終わって二つ目の予測が始まると、
走っている一つ目の予測が取り消される。手動で起動した後に予約の起動が順番待ちに来たら、
予約の起動を取り消す（中身は同じ）。2026-10-05 に予約の起動をやめたので、この重なりは
もう起きない。手で起動するなら Routine の時刻（平日 18:40 JST）と重ねない。

**2026-10-05 に予約の起動（cron）そのものをやめた。** 10/5（月）は 07:05 UTC の予約が 14:33 UTC
（23:33 JST）になっても来ず（+7h28m 超）、運用者の了承で手動起動した（run 37325682385。予測 run
37326163279、23:43 JST に公開）。遅れが翌日にかかる日が出てきたので、cron を外し、Claude の Routine が

### 当日データが出るまで待つ

**定刻に起動してしまった日のために待つ**。前倒しすると、たまたま遅延が
小さかった日に「まだ当日データが無い」状態で走ることになる。2026-10-05〜10-07 は
Routine が 16:10 JST に起動したので毎回ここで待った（四本値は 16:00 までに出ているが、
指数・TOPIX は 16:30）。10/8 からは 18:40 の起動で、ふだんは待たない（締切 18:00 を
過ぎているので1回確かめて進む）。待つのは大引け後〜18:00 に手で起動したとき。`wait=no` で起動したとき（過去分の取り直し）と、大引け前の起動
（翌朝の確認の Routine が前日ぶんを起動し直したとき）は待たない。
`research/wait_for_data.py` を取り込みの前に挟み、**四本値・業種別指数・
TOPIX** が出るまで待つ（締切 18:00 JST。実測 16:30 に対して1時間半の余裕）。

四本値だけでは足りない。`build_dataset` は業種別指数と TOPIX を
`merge_asof(direction="backward")` で結合するので、**その日の行が無いと
欠測にならず前日の値が入る**。気づけない形で質が落ちるので、ここは待つ。

決算開示（18:00）は待たない。1時間半の遅れに見合わないと判断した。
取りこぼしても失われはせず、翌営業日の取り込みで入る（下記）。
**ただし、その日の予測には欠ける。** 学習の行は後から作り直すのでその日の決算が入り、
予測の行には入っていない（学習と予測の食い違い）。2026-10-07 の一致チェックで空売り比率に
出たので、取り込みの起動を 18:40 に移した（上の「取り込みを 18:40 に移した」）。
同じ日に入れたければ、ワークフローの `--feeds` に `fins` を足して
`--deadline` を 18:30 にすればよい。

締切まで出なくても**止めずに先へ進む** — 祝日・臨時休場はそもそも
当日データが存在せず、ここで落とすとその日だけパイプライン全体が
止まるため。古いデータで予測する事故は鮮度チェックが見ている。

### 公表前に叩いた日を「取得済み」にしない

差分取得の記録（`manifest.json` の `fetched_days`）は**行数ではなく
「その日を叩きに行ったか」**で付けている。財務のように開示が0件の日を
毎回叩き直さないためだが、そのままでは**公表前に叩いた日も取得済みに
なる**。`missing_days` は「候補 − 記録」なので、一度記録した日は二度と
候補に入らない。つまりその日のデータは永久に失われる。

21:30 起動のときは四本値・指数・財務がすべて出そろっていたので表に
出なかったが、**信用残では既に起きていた**。保存データを確認すると
記録は 2026-09-07 まであるのに、実データは 2026-08-28 が最後だった。
週次公表を待たずに叩いた週が、取得済みとして記録されて消えている。

そこで種別ごとに公表ラグを持たせた（`data_store.PUBLISH_LAG_DAYS`）。
**0件で返り、かつ公表ラグの中にある日は記録しない**ので、次回また
取りに行く。ラグを過ぎても0件ならそれは本当に0件（祝日・開示なし）と
みなして記録する — そうしないと永久に叩き続けることになる。

| 種別 | 猶予 | 理由 |
|---|---|---|
| 四本値・指数・TOPIX・財務・マスタ履歴 | 当日のみ | 同じ日のうちに出る |
| 信用残 | 10日 | 週次。金曜ぶんが翌週に出る |

この仕組みがあるので、公表前に起動しても財務のデータは失われない
（1営業日遅れて入るだけ。ただしその日の予測には欠けるので、取り込みは 18:40 に起動する）。

### 信用残の穴を数え直した（2026-09-18）

記録を見ているだけでは気づけないので、保存データの側から数えた。
10年ぶん519週のうち、**32週**が空いていた（範囲内の30週＋直近2週）。
内訳は3つに分かれる。

| 原因 | 週数 | 取り直しで戻ったか |
|---|---|---|
| 公表ラグ（上節） | 2 | 戻った |
| 叩く日が違っていた（下記 (1)） | 23 | 17週が戻った。残り6週は (3) |
| J-Quants に元々無い（下記 (3)） | 13 | 戻らない（7週＋上の6週） |

**(1) 金曜が祝日の週（23週）。** 残高はその週の**最終営業日**時点のもの。
ふつうは金曜だが、金曜が休場なら木曜になる。旧コードは「金曜を全部足し、
金曜が無い週はその週の適当な日を足す」としていて、この「適当な日」が
週の**先頭**（多くは月曜）だった。月曜を叩いて0件、そのまま取得済み。
`jq_bulk.margin_candidates()` に切り出して、週の最終営業日を選ぶようにした。
`fetch_margin` と差分取得の2か所に同じ間引きを書いていたのも、ここで1つに
まとめてある（二重に持つとずれる）。

**(2) 問い合わせ自体が失敗した日。** これは上の30週を**説明しない** ——
コードを読んでいて見つけた別経路で、実際に起きた形跡は確認していない。
`_fetch_by_day` は失敗した日を読み飛ばして件数だけ出していたが、記録は
要求した日すべてに付いていた。一過性の 503 で1営業日ぶんが永久に失われる
経路なので、失敗した日を `LAST_FAILED_DAYS` で持ち回して記録から外した。

**(3) J-Quants 側に元々無い週（13週）。** (1) と公表ラグを直して全期間を
取り直した結果、**19週が戻り**、13週は取り直しても0件のままだった。

```
2017-05-02(火) 2018-01-05(金) 2018-05-02(水) 2019-01-04(金) 2019-12-30(月)
2020-05-08(金) 2021-05-07(金) 2022-05-06(金) 2023-05-02(火) 2024-01-05(金)
2024-12-30(月) 2025-12-30(火) 2026-05-08(金)
```

**13週すべてが GW・正月明け・年末の、営業日が1〜2日しかない週**。
例外なくこのパターンなので、J-Quants がこれらの週の残高を公表していない
ものと判断した（公式ドキュメントが読めないため、根拠は実測のこの規則性
だけ）。公表ラグ（10日）を過ぎた過去の週なので「本当に0件」として記録され、
毎回叩き直すことにはならない。

### 失われたぶんを取り直す

**自動では戻らない。** 記録済みの日は候補に入らないので、記録を外してやる
必要がある。`Update Data Store` を手動起動し、`forget` に種別を入れる
（範囲を絞るなら `forget_from` に開始日）。

```
forget      = margin
forget_from =            ← 空なら全期間
```

`--forget` は**取得記録だけ**を外す（`--reset` と違って parquet は消さない）
ので、取り直せなければ現状のまま何も変わらない。

信用残は `credit_ratio` の元で、staleness の上限が無い。実データが
2026-08-28 で止まっていたため、8月29日以降のサンプルはすべて 08-28 の値を
使っていた。2026-09-18 の取り直しで **486週 → 505週**（2016-10-07 〜
2026-09-11）になり、直近まで埋まった。所要は519週ぶんで約14分。

## なぜ学習を週の境目に置くのか

予測は毎営業日の夜に出るが、モデルは**週に1度しか差し替えない**。しかも
差し替えるのは日曜、つまり月〜金のどの予測も挟まない位置に置いてある。

週の途中で差し替えると、その日の候補が前日までと比較できなくなる。
スコアが動いたのが「相場が変わったから」なのか「モデルが変わったから」なのかを
切り分けられず、順位も較正確率もスコア帯の実績も、日をまたいで読めなくなる。

```
  日曜の朝   モデルを作り直す（予測はしない）
  月〜金の夜 5日とも同じモデルで採点する
```

この理由から、**日曜には予測を走らせていない**（`Retrain Weekly` を
`Predict Breakouts` の `workflow_run` に繋いでいない）。日曜に予測すると、
金曜引け基準の同じ候補が金曜夜とは別のモデルでもう一度出ることになり、
どちらを見ればよいのか分からなくなる。新しいモデルは月曜夜の予測から効く。

切り分けられなくなるのが唯一の副作用なので、`research/lgbm_params.json` の
差分を毎週の実行要約に出してある。何が動いたかは毎週その場で見える。
ファイル自体も毎週コミットされるので、git の履歴で遡れる。

### 測り直し（2026-09-17 / `research/exp/e17_etf.py`）

物差しを運用に合わせ、種3個の確率平均で測り直した。

**上位10%に選ばれた2,000件の内訳**（現行＝ETF込みで学習・採点）

| | 件数 | 構成比 | 実収益 中央 | 平均 | 勝率 | 25%分位 |
|---|---:|---:|---:|---:|---:|---:|
| ETF等 | 502 | 25.1% | **+2.79%** | +2.38% | **67.7%** | **-1.73%** |
| 株式等 | 1,498 | 74.9% | +2.24% | **+3.58%** | 59.7% | -3.62% |
| 全体 | 2,000 | 100% | +2.52% | +3.28% | 61.7% | -3.18% |

**ETF のほうが中央値も勝率も高く、下振れも浅い。** 株式のほうが平均は高い
（裾が厚い）。

この節を最初に書いたとき、「安定した少額の利益を狙うなら ETF は外すべき
ではない」と結論した。**これは前提を取り違えていた**。「安定した少額の利益」
は株式の運用についての話で、この仕組み全体の目標ではない。この仕組みは
値幅を取りにいくものなので、中央値が高く平均が低い ETF は噛み合わない。
実測の数字はそのまま（上の表は正しい）で、そこから引いた結論だけが誤りだった。

**学習から外しても効果は無い**（評価母集団を揃えた比較）

| 条件 | 窓平均 | 標準誤差 | 勝ち窓 | 最悪の窓 |
|---|---:|---:|---:|---:|
| A  学習=全部 / 評価=全部（現行） | +0.80pt | 0.32 | 7/9 | -0.73pt |
| A' 学習=全部 / 評価=株式のみ | +1.17pt | 0.26 | 9/9 | +0.17pt |
| B  学習=株式 / 評価=株式のみ | +1.28pt | 0.33 | 9/9 | +0.22pt |

A' と B の差は **+0.11pt / z=0.27 で差なし**。つまり **ETF を学習データから
外す意味は無い**（外すなら候補から落とすだけでよく、再学習は不要）。

A と A' の差（+0.37pt / z=0.90）も足切りを越えないが、勝ち窓が 7/9 → 9/9、
最悪の窓が -0.73pt → +0.17pt に変わる。ただし勝率は 61.7% → 57.8% に**落ちる**。
安定性を取るか、負ける窓を消すかのトレードオフで、平均リターンはほぼ同じ
（+3.28% → +3.22%）。

**上位10%に占める ETF 比率は窓ごとに 5.8%〜57.8% と大きく振れる。**
買う対象の構成が週によって入れ替わるので、そこが気になるなら外す理由になる。

**読むときの注意**: 正例率はボラで大きく歪むが実収益は歪まない。つまり画面と
スプレッドシートの**較正確率・帯の正例率は、低ボラ銘柄で系統的に楽観側にずれる**。
帯の実収益（`bandEndMedian`）のほうが素直に読める。

**外した**（2026-09-17）。母集団の定義そのものから落とす形にした。
`research/build_dataset.py` の `EXCLUDE_MKT_CODES`（既定 `(109,)`）で、
`mkt_code` を結合した直後に1箇所で切っている。学習データ・OOF（スコア帯と
較正表の元）・日次予測の候補が同じ1行で揃うので、母集団が食い違わない。

A' と B に差が無い以上、学習から外すこと自体に効果は期待していない
（期待しているのは A→A'、つまり候補から外すぶん）。それでも1箇所で切るのは、
帯の正例率や較正確率を**候補と同じ母集団**で作り直すためで、
学習だけ ETF 込みのまま残すと帯と候補がずれる。

効き始める時点は非対称になる:

| | 変わる時点 |
|---|---|
| 日次予測の候補から ETF が消える | このコミットの次の Predict Breakouts から |
| スコア帯・較正確率が株式だけの母集団になる | 次の Retrain Weekly（日曜）から |
| 「開示からの日数」（`days_since_disc` / `days_since_fy`）が特徴量に入る（2026-09-22 に採用。`docs/MODEL_DISCLOSURE_TIMING.md`） | 次の Retrain Weekly（日曜）から 153列。日次予測は meta.json の特徴量一覧で採点するので、それまでは旧モデル（151列）のまま |

戻したいときは `EXCLUDE_MKT_CODES = ()`（または環境変数
`SWEEP_EXCLUDE_MKT_CODES=none`）。実際に効いた設定は
`dataset_meta.json` の `excludeMktCodes` に残る。
母集団は 22,887 → 21,138件（-1,749件 / -7.6%）、
正例率は 20.85% → 19.93% になった。

**過去ぶんの見分け方**: 除外は今後の予測にだけ効くので、
スプレッドシートに既に入っている ETF の行は残る。業種が「その他」で
時価総額が空欄の行がそれ。

- 書く（モデル別・追記時に1度）: LGB% / XGB% / CAT% / LGBスコア / XGBスコア / CATスコア / 一致(上位10%)

**翌営業日始値**（2026-09-25 に追加）は、予測日の次の営業日の始値。運用の規則は
「翌営業日の寄りで買う」なので、収益はこの値を基準に数える。予測時株価・現在値と
同じく分割調整なしの、その日に実際に付いた値。予測した夜にはまだ無く、次の営業日の
日足を取り込んだ夜に入る（連休をまたぐときは連休明けの始値）。寄り付かなかった日は
空のまま。一度入った値は書き直さない。既存のシートでは見出しの右端に足されるので、
見やすい位置へ手で動かしてよい（名前は変えないこと）。なお「騰落率%」は今も
予測時株価（予測日の終値）が基準で、翌営業日始値からの値ではない。

列は**見出しの名前で探す**。途中に自分用の列を挿しても壊れない。
行は追記のみで、既存行を作り直さない（作り直すと手入力が消える）。

### モデル別の列の読み方

2種類ある。

| 列 | 中身 | 使い方 |
| --- | --- | --- |
| `LGB%` など | そのモデル自身の**過去スコア分布での位置**（0〜100）。画面の棒グラフと同じ値 | **モデルをまたいで比べられるのはこちらだけ** |
| `LGBスコア` など | モデルが出した**生の値** | 同じモデルの中で日をまたいで追う／自分でしきい値を引き直す |

**際どい候補の印（2026-10-10）。** 運用者の線「3モデル（lgbm・xgb・cat）とも95以上」の下で、「2つが95以上で残り1つが95未満」
か「3モデルの最小が85〜95」の候補に「際どい」の印と一番低いモデルを出す（候補一覧の行・今日の戦略の買い候補・惜しい候補。
`src/lib/strategy.js` の `BORDER` / `borderNote`）。2つが95以上で LightGBM が一番低いときだけ赤で「過去ほぼ 0%」
（実験70: 145件で 0.0%、XGBoost / CatBoost が一番低いと 420件で +1.8%）。それ以外は黄で、その形の過去の数字を添える。
行を開くと先頭に全文が出る。選定の規則（戦略パネルの 90 の線）は変えていない。数字は `BORDER_STATS` に置き、
モデルを作り直して実験70 を回し直したら差し替える（docs/PLAYBOOK.md「実験70」）。

画面の百分位の色は1つの色相（青）の濃淡で、区分は 95以上（上位5%。運用の選定「lgbm 単体 95以上」の線）・90以上（「3モデル 90以上」の線）・80以上・60以上・30以上・それ未満の6つ（`src/lib/predictions.js` の `PCT_TIERS` / `pctColor`、色は `styles.css` の `--pct-*`。暗い画面なので上の区分ほど明るく鮮やか）。2026-10-09 の運用者の指示: まず「上位5%を基準にするので紫とは別の色で区分を増やす」→ 95 以上をシアン、次に「シアンと緑が見分けづらい」→ ピンク、最後に「30 / 60 / 80 / 90 / 95 で分けて色は濃淡で」→ いまの形。低い区分は暗くて文字には使えないので、文字は塗らず四角（`.pct-sw`）を添える。帯（10分位）の色は別のまま。

**生スコアはモデル間で大小を比べてはいけない。** 実例（2026-09-11 の1699）。

| | LGB | XGB | CAT | LR | NN |
| --- | ---: | ---: | ---: | ---: | ---: |
| 位置% | 90.3 | 89.4 | 94.4 | 54.4 | 84.3 |
| 生スコア | 0.535 | 0.474 | 0.615 | 0.500 | 0.294 |

NN の生スコア 0.294 は LR の 0.500 より小さいが、**位置は NN 84.3 > LR 54.4**。
学習器ごとに確率の出方が違うためで、生スコアの大小には意味がない。

位置だけだと後から別のしきい値で切り直せない（順位に潰れている）ので、
生スコアも併せて残してある。

既存の `スコア` 列は基準モデル（LightGBM）の生スコアで、`LGBスコア` と同じ値。
運用開始時から入っている列なので、過去行との連続性のために残してある。

`一致(上位10%)` は上位10%と見ているモデルの数（例 `3/5`）。独立した判定の
数え上げで、スコアを混ぜた値ではない。**平均は出していない** — 混ぜた数字を
1つ出すと、呼び名が何であれアンサンブルになるため。

`順位 / 帯 / スコア / 較正確率%` はすべて**基準モデル（LightGBM）**のもので、
`LGB%` と同じモデルを指す。モデル別の列は隣に並べる参考値で、順位には効かない。

読むときの注意（実測・`docs/MODEL_LINEUP.md`）。

- 木3つ（LGB / XGB / CAT）は互いに相関 0.80〜0.89、上位10%の重複 50〜58%。
  **揃って高くても独立した3票ではない**
- 木以外2つ（LR / NN）は互いに 0.823。塊をまたぐと 0.63〜0.71 に落ちる
- **塊をまたいで揃ったとき**だけ、見方の違うモデルが同じ結論に達したと読める

## 営業日カレンダー（2026-09-22 に入れた）

### 何が起きたか

2026-09-21（敬老の日）〜09-23（秋分の日）の3連休で、日次予測が赤で落ちた。

```
[freshness] 日次バーの最終日 2026-09-18 / 基準日 2026-09-22 / 遅れ 2営業日（許容 1）
[fatal] 生データが古すぎます
```

落ちた経路は2つある。

1. **鮮度チェックが遅れを平日で数えていた。** `np.busday_count` は祝日を
   知らないので、連休では遅れを多く見積もる。3連休だと許容の1を超える
2. **営業日ゲートが manifest の鮮度（12時間以内）を条件にしていた。**
   連休2日目は**その日の取り込みがまだ走っていない**ので使えない。
   実測で manifest は18時間前だった

### どう直したか

**`/markets/calendar` の応答を保存するようにした。** 取り込み
（`jq_bulk.trading_days`）は元からこのエンドポイントを叩いて営業日を
決めていた。叩いているのに捨てていただけ。

| 部品 | 役割 |
|---|---|
| `research/trading_calendar.py` | 保存・読み出しと、営業日の数え方 |
| `research/_data/calendar.parquet` | `Date` と `HolDiv`。Release にも載る |
| `research/check_freshness.py` | カレンダーで数える。無ければ平日（厳しい側） |
| `research/trading_day_gate.py` | カレンダーで判定。範囲外なら manifest に落ちる |

**先の日まで取っておく**（`CALENDAR_LOOKAHEAD_DAYS = 45`）。下流は「今日」が
カレンダーの範囲に入っていないと使えず、取り込みが当日まだ走っていない
時刻に予測が動くことがあるため。取りに行く対象は従来どおり end まで。

### カレンダーを言い訳にしないための決め事

元のコードには「ここで祝日カレンダーを持ち込むと、更新が止まったときに
『祝日だから』と自分で言い訳する余地を作ってしまう」というコメントがあった。
**その懸念は自分で推測する場合の話**で、いまは取引所が公表した事実を読む。
それでも緩まないように、こう決めてある。

- **カレンダーが対象日を覆っていないときは使わない。** 平日で数える側に倒す
- **カレンダーが「営業日だ」と言っている日にデータが無ければ、遅れとして
  数える。** 祝日を持ち出せるのは、取引所が非営業日だと言った日だけ
- ゲートは、保存データが**カレンダー上の直近の営業日に届いている**ことまで
  確かめてから飛ばす。取り込みが壊れていれば休場日でも飛ばさない
- ファイルが無くても壊れていても例外を投げない。ここが新しい障害の
  入口になってはいけない

### 予測済みの日を予測し直さない（2026-09-24 に直した）

**ゲートは壁時計の日付ではなく「まだ予測していない日足があるか」で決める。**
それまでは「今日（日本時間）が営業日か」で決めていたため、次の2回、予測済みの 9/18 を
新しいモデル（9/20 学習）で予測し直し、追跡記録に当時は選んでいない銘柄（日本ナレッジ）を足した。

| 日時（JST） | 起動 | 起きたこと |
|---|---|---|
| 9/24 0:09 | 手動（休場日の確認のつもり） | 日本時間の翌日（営業日）と判定され最後まで走った（run 35879476135）。500e3c6 で取り除いた |
| 9/24 3:24 | **自動**。休場日 9/23 の取り込みが日付をまたいで終わり、連鎖した予測が走った | 同じ1件が再び入った（1f18614）。2026-09-24 に取り除いた |

2回目は手動の注意書きでは防げない形だった。直したこと:

1. **ゲート**（`research/trading_day_gate.py`）: 保存データの最終バー日が、公開済みの
   `predictions.json` の `asOf` より新しいときだけ予測する。新しくなければ飛ばす。
   営業日の 18:00 JST（取り込みの待ちの締切）を過ぎてもその日の日足が無ければ、
   飛ばしたうえで**最後に赤にする**（`Fail if bars are missing`）。休場日でも未予測の日足が
   あれば予測する。意図して予測し直すときは `workflow_dispatch` の `force`
2. **追跡記録**（`predict_daily.update_history`）: その日の記録が1件でもあれば後から足さない
   （最初の予測で凍結）。現在値などの追跡列は更新を続ける
3. **経過日数**: 追跡記録と台帳の「経過営業日」を、平日ではなく取引所の営業日で数える
   （連休3日を経過日に数えていた）
4. テストで固定した（`tests/test_trading_calendar.py` の `TestNoRepredict`、
   `tests/test_prediction_record.py`）。CI は `tests/` の全部を回すようにした（下記）

台帳（スプレッドシート）は全候補を1行ずつ持ち、モデル別の列は空のセルにしか書かないので、
予測し直しで当時の値が書き換わることは無い（`tests/test_sheets.py` が固定している）。

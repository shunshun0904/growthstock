# M&A・TOB の特徴量: 情報源の下見と判断（2026-10-03）

運用者の依頼「M&A の特徴量を入れてもよい。現状それ関連は何か入れているか。何もなければ
https://maonline.jp/db/companies/ からクローリングして取得してほしい（リクエスト頻度は落として）」。

## 結論を先に

1. **いまの 239列に M&A・TOB そのものの列は無い。** 近いのは 大量保有報告書（`lvs_*`）、大株主の構成（`mjr_*`）、
   持ち合い（`xh_*`）、業績予想の修正（`rev_*`）。TOB は 20日ボラがゼロになる形で間接的に見えるだけ
   （実験63: 全5モデル 95以上の 97件のうち TOB で値が止まった 2件はどちらも外れ。画面に「値動きなし」の注意を出した）
2. **M&A Online（maonline.jp）はクローリングしない。** 利用規約 第16条（禁止事項）(5) が
   「弊社の事前の書面による承諾がある場合を除き、スクレイピング、クローリング等の自動化された手段を用いて本サービスへ
   アクセスすること」を禁じている。robots.txt は `/db/` を一般のクローラに禁じていないが、規約が優先。
   頻度を落としても「自動化された手段」には変わりない。使うなら M&A Online（ストライク社）に書面で申請してから
3. **代わりに公式の EDINET API（金融庁）を提案する。** 公開買付届出書・意見表明報告書・公開買付撤回届出書・
   臨時報告書の提出一覧が無料で取れ、規約の心配がない。TOB の対象になった日はここが一次情報。
   必要なのは EDINET API の利用申込（無料。いまの `EDINET_API_KEY` は EDINET DB（edinetdb.jp）の鍵で別物）

## 代替案: EDINET API（金融庁）から作る列

EDINET API は提出書類の一覧（日付ごと）と書類本体を返す。一覧には提出者の EDINET コード・証券コード・書類種別と、
公開買付関係では発行者（対象会社）の EDINET コードが入る。書類種別コードは実装時に仕様書（書類種別コード表）で確かめる
（ここでは名前だけ書く。記憶で番号を書かない）。

| 列（案） | 元の書類 | 意味 |
|---|---|---|
| `tob_target_days` | 公開買付届出書（対象会社 = その銘柄） | 直近の TOB 届出からの日数。小さいほど TOB 中。実験63 の「値動きなし」を一次情報で裏づける |
| `tob_active` | 公開買付届出書・公開買付撤回届出書・公開買付報告書 | 届出があり、撤回も報告（完了）もまだ無い = TOB 中（0/1） |
| `tob_opinion` | 意見表明報告書 | 対象会社の賛同 / 反対 / 留保（本文の解析が要る。まずは提出の有無だけ） |
| `ma_filer_n_250` | 臨時報告書（合併・株式交換・子会社取得など） | 直近250暦日にその銘柄が提出した M&A 関係の臨時報告書の件数。買収で伸びる会社の代理 |
| `ma_days` | 同上 | 直近の M&A 関係の臨時報告書からの日数 |

注意

- 臨時報告書は提出事由が複数あり（決算の変更・主要株主の異動・災害など）、M&A だけを選ぶには本文（XBRL）の提出事由を
  読む必要がある。まず公開買付関係の 3列から始め、臨時報告書は提出事由の解析ができてから
- 一覧は提出日単位で取るので、時点整合は自然に守れる（提出日より前の行には付かない）
- 期間: API の一覧がどこまで遡れるか（学習データは 2018年〜）は申込後に実測する
- 取り込みは J-Quants と同じ形（日次の Actions、差分、Release に保存）。1日 1リクエストで足りる。過去分は
  日ごとの一覧を 8年分 ≈ 2,000 リクエストで一度だけ

## 次の手順（運用者の判断待ち）

1. EDINET API の利用申込をする（金融庁の EDINET から、無料）→ 鍵を GitHub の Secrets に `EDINET_FSA_API_KEY` として入れる
2. こちらで取り込み（`research/edinet_api_fetch.py`）と特徴量（上の 3列）を作り、実験で §7 の手順どおり測る
3. M&A Online を使いたい場合は、先方に書面で申請する（こちらからは申請しない）

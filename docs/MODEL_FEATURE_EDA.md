# 全特徴量の点検（実測・2026-09-22）

運用者の指示「学習や検証に入る前に改めて全特徴量の EDA をお願いします」に対する記録。

- 列そのものの性質（欠損・外れ値・分布・冗長）: `research/eda_stats.py` → `research/eda.json`
- 検出力（その列に意味があるか）: `research/exp/e40_feature_eda.py` → `research/_data/oof/e40_feature_eda.csv`

母集団 21,856件 / 銘柄 3,735 / 2018-04-03〜2026-08-21。
物差しは `ret_o1_20`（翌日始値で入り、20営業日後の5日平均終値で出る）。
**205列すべてを測っている**（バックフィル完了後の実データ。取り込み待ちは無い）。

## 測り方

実験20・23 と同じ。本番の out-of-fold と同じ11窓（36ヶ月訓練 / 6ヶ月テスト /
6ヶ月刻み、エンバーゴ20営業日）で、窓ごとに

- **上位 z** … その列の上位10%の実収益が、同じ窓の平均をどれだけ上回ったか
- **下位 z** … その列の下位10%の実収益が、同じ窓の平均をどれだけ上回ったか

を取り、11窓ぶんの 平均 ÷ 標準誤差 を z とする。足切りは |z| > 2。
ノイズ床は 0.143pt（実験11）。

特徴量が205本あるので偶然の |z|>2 は数本出る。**1本だけの |z|>2 は採らず、
同じ群の中で符号が揃うかで読む。**

## 結論を先に

1. **買う理由になる列は21本、見送る理由になる列は46本。** 片側にしか効かない列が
   多いという実験37 の結論が、全特徴量でも成り立つ
2. **足した52列のうち16本が足切りを超えた。** いちばん強いのは
   `rev_up_n_250`（直近250暦日の上方修正の回数、#45）で、上位 z=+4.06 /
   下位 z=−3.62 の単調な形。**本番の153列を含めた205本の中でも上位**
3. **23列は「銘柄の選別」ではなく「時期の選別」を測っている。** 同じ日なら
   どの銘柄でも同じ値であることを実測で確かめた。`market` 群の11列に加え、
   今回足した `short_ratio` 2列と `inv_*` 10列がこれに当たる。
   新規列で最も強く出た `inv_prop_4w`（−3.69）・`inv_foreign`（+2.94）も同じ
4. **年ごとの欠損率には2種類ある。** 初年度（2018）の欠測は履歴不足で、
   評価窓の外なので無害。一方 `lvs_*`（大量保有・2021-07〜）と
   `xh_*`（政策保有・2020-05〜）は**制度として途中から始まる**列で、
   評価窓の中にかかる
5. **点検の過程でバグが3本見つかった。** うち2本は「データは全部あるのに列が
   壊れている」型で、欠測率と冗長検出を見なければ気づけなかった（§7）

空売り比率は API が S33=9999（全市場）の1系列しか返さない（実測 2,434行 =

## 7. 点検で見つかったバグ

### 7-1. ラベルの内訳が壊れていた（eda_stats.py）

直前まで「到達 2,293件 → 正例 3,865件」という**到達より正例が多い**数字を
出していた。原因は `label_stats` が固定の `cfg.threshold`（20%）で到達を
測っていたこと。本番のラベルはボラ正規化なので実際のしきい値は行ごとに違い、
**80.3% の行で 20% より緩い**（中央値 10.95%）。
`build_dataset.rise_thresholds` が式の正本なので、`vol_20d` からそこを
呼んで引き直す形に直した。

直したあとの内訳:

| | 件数 | 割合 |
|---|---:|---:|
| 母集団 | 21,856 | 100% |
| 到達 | 5,176 | 23.7% |
| 正例 | 3,865 | 17.7% |
| 到達したのに継続条件で落ちた | 1,311 | 到達の25.3% |
| 到達していないのに正例 | 0 | — （整合） |

`build_dataset` は `rise_need` を列として残しているが `FUTURE_COLS` に
入っていないため、データセットには出ていない。`vol_20d` は残るので、
後段は必ず `rise_thresholds` から引き直すこと。

### 7-2. 入れ子の列が ndarray で来て、mjr_* 7列が全欠測だった

`mjrshld` を 77,730行 取り込んでいるのに `mjr_*` 7列が**充足 0.0%**。
`_holders` が `list/tuple` しか見ていなかったが、pyarrow の list 型は
読み戻すと **`numpy.ndarray`** になる。実データの `Hldrs` は 8,155行すべて
ndarray で、欠損は1行も無いのに全部捨てていた。

**データが1行も欠けていないのに 0% になる**という、いちばん気づきにくい
壊れ方。取り込みも保存も成功していて、どこにも例外が出ない。
修正後の充足は 99.9%。

### 7-3. API の ROE / FwdROE は小数。単位を揃えずに引いていた

実験40 の冗長検出が拾った。`jq_roe_gap` と `ROE_q0` の相関が **−0.9999**。
実測（valuation_2025）:

```
API の ROE     中央値 0.0798
API の FwdROE  中央値 0.0791
FwdEPS / BPS   中央値 0.0791   ← FwdROE と一致
```

つまり API の ROE / FwdROE は**小数**（0.0791 = 7.91%）。自前の `ROE_q0` は
**%**（中央値 5.71）。小数から%を引いていたので `jq_roe_gap ≒ −ROE_q0` に
なっており、「予想と実績の差」をまったく測れていなかった。

直した結果、`jq_roe_gap` の z は +0.52 / −0.90 で**検出力は無い**。
バグが作っていた見かけの信号が消えたのであって、直して弱くなったのではない。
PER / PBR / EPS / BPS は自前と同じ単位（倍・円）であることも実測で確かめた。

# 特徴量の時点整合 —— 「その値を予測の時点で知りえたか」

特徴量の値は、**予測の時点で公表済みだったもの**でなければならない。学習用の
データセットは後から作り直すので、記録の日付（基準日・集計期間の末日）で結合すると、
学習だけが公表前の値を見ることになる。予測では同じ新しさの値は手に入らない。

各データの「使ってよい日」は `research/availability.py` の1か所で決め、
`tests/test_availability.py` が種別ごとに「公表日の前日までは前の値、公表日から
新しい値」を確かめる。日次予測は、その日に使った特徴量を控えて、翌日以降に
作り直した値と毎日比べる（`research/check_train_serve.py`、下記）。

## 結論を先に（2026-09-24）

- **2か所で公表前の値を学習に使っていた。** どちらも直した
  | 特徴量 | 公表 | 以前の結合 | 公表前の値を使っていた行 |

  | 投資部門別 `inv_*` 10列 | 集計期間の末日の約6日後（`PubDate`） | 集計期間の末日 | 85.7% |
- 同じ生データで直す前と後のデータセットを作って比べると、**違うのはこの12列だけ**
  （`inv_*` 10列が 85.69%、`credit_ratio` 38.48%、`credit_ratio_r` 30.47%）。
  行（21,856行）も、残りの341列（キーの Code・Date を除く353列のうち）も1つも変わらない
- **実運用ではずれがもっと大きかった。** 9/10〜9/18 に画面に出た信用倍率は、
  候補すべてが **8/28 の週**の値だった（取り込みの取りこぼしで 9/4・9/11 の週が
  まだ入っていなかった）。学習は同じ週（未公表）の値を見ていたので、ずれは最大3週間

## データごとの「使ってよい日」

日次予測は取り込みの後に走る（平日 21〜23時 JST が実績。遅れた日は翌日未明）。
その日の夜までに取り込めるものは当日から使ってよい。

「出た時刻」は Probe Update Time（`research/probe_update_time.py`）の実測。16:00 JST から
30分おきに当日ぶんを問い合わせ、最初に行が返った時刻を記録する（16:00 の値は
「16:00 の最初の問い合わせで既にあった」の意味で、それより前に出ていた可能性がある）。

| 種別 | 使ってよい日 | 根拠（出た時刻） | 状態 |
|---|---|---|---|
| 日足・業種別指数・TOPIX | 当日 | 日足 16:00、指数・TOPIX 16:30（9/18・9/24 とも同じ） | 確認済み |
| 銘柄マスタ（月次） | 当日 | 16:00 | 確認済み |
| 決算（`DiscDate`） | 当日 | 18:00 ごろ（9/18。9/24 は 18:02 に19行、20:03 まで増えず） | 確認済み。取り込みが 18:00 より前に走った日は翌日にずれるので、日次の食い違い確認で見る |
| 信用残（週次） | 基準日の翌週 **第2営業日** | JPX の週次公表 | **直した**。9/24 は連休明けの第1営業日で、9/18 ぶんは 20:00 までに出なかった（規則どおり）。第2営業日の 9/25 の Probe Update Time（run 36099557178、14:40 JST 起動・20:30 まで）は、ジョブの上限（350分）の 20:30:43 に殺され、出力も溜めたまま消えて何も残らなかった（`python3 -u` と `--max-minutes` で直した）。代わりに 9/25 夜の取り込みで確かめた: **9/18 ぶん（4,262行）は 9/25 夜の取り込み（Update Data Store run 36136560479、21:43 JST 起動）で入り**、同じ夜の予測（Predict Breakouts run 36136887499）に間に合った。第2営業日のままでよい。公表の時刻そのものは測れていない（21:43 より前に出ていたことだけが分かる） |
| 投資部門別（週次） | `PubDate` | J-Quants の公表日の列 | **直した**。9/24 は公表日が当日の行が 20:00 までに無かった（週次なので公表日でなかった可能性がある） |

| バリュエーション | 当日（`Date`） | 16:00（9/24、4,450行） | 確認済み |
| 空売り比率（業種別。`short_ratio` は「その他」業種、`short_ratio_mkt` は全行の合計） | 当日（`Date`） | 16:30（9/24、34行） | 確認済み |
| 空売り残高報告（候補。実験44で採用しなかった。`docs/MODEL_ADOPTION_RULES.md` §9） | 公表日（`DiscDate`）の**翌営業日** | 18:02（9/24、1,340行） | 翌営業日のまま（`availability.SHORTSALE_SAME_DAY = False`）。夜の取り込みには間に合うが、取り込みが定刻（16:05 JST）どおりに起動した日には間に合わない。1日遅れる代わりに、取り込みの時刻に左右されない。取り込みは続ける |
| 大量保有・大株主・政策保有 | 提出日（`SubDate`） | 16:00 に最初の行が出て、**17:31 まで増えた**（大量保有 112→120→121→123行、大株主 37→45→48行、政策保有 36→44→47行。16:00 / 16:30 / 17:00 / 17:31 の値） | 当日のまま。17:30 より前に走った取り込みは一部しか取れないので、**今日の日は取得済みにしない**ようにした（下記） |

**9/24 の夜の取り込み（21:41 JST 起動）は、当日ぶんを実測の最終値どおりに保存していた。**
Release の保存データで 9/24 の行を数えると、バリュエーション 4,450・決算発表予定 93・
大量保有 123・大株主 48・政策保有 47・空売り比率 34・決算 19・空売り残高報告 1,340 行で、
Probe Update Time の 20:03 の値と全部一致した。信用規制だけは 0行で、これはその夜も
保存に失敗していたため（下の「保存に失敗し続けていた2種別」。全期間を取り直し中）。

**今日の日は取得済みにしない（2026-09-24 から）。** 取り込みは「叩きに行った日」を
取得済みとして記録し、次からはその日を問い合わせない。今までは今日の日も、行が
取れれば取得済みにしていた。EDINET の3種別は 16:00〜17:31 に行が増えるので、それより
前に取り込みが走ると、後から来た行を二度と取りに行かない。いまの取り込みは GitHub の
起動の遅れで毎日 21〜23時に走っているので実害はまだ無いが、定刻どおりに起動する日が
あれば起きる。今日の日は行が取れても記録せず、翌日の取り込みでもう一度取る
（`jq_bulk._record_fetched`。行のキーで重なりは1行になるので、取り直しても行は増えない）。
`tests/test_data_store.py` の `TestRecordFetched` が確かめる。

## 見逃さないための仕組み

1. **1か所で決める**: `research/availability.py` の `RULES`。取り込む種別を足したのに
   ここに行が無いと、`tests/test_availability.py` が落ちる
2. **結合の結果をテストする**: 公表日の前日の行に新しい値が入っていたら落ちる。
   直す前のコードに同じ入力を通すと、このテストは落ちる（確かめてある）
3. **毎日、予測に使った値と作り直した値を比べる**: 日次予測はその日の特徴量を控え
   （`live_features.parquet`、Release）、翌日以降の実行で、作り直したデータセットの
   同じ行と比べる。違いが許容（1%）を超えた列があれば、その段が赤になる
   （画面の更新は止めない）。公表前の値での結合、予測の時刻より後に届いたデータ、
   データの後からの訂正のどれでも値が変わるので、ここで捕まる
4. **CI は tests/ の全部を回す**（2026-09-24 から。`docs/OPERATIONS.md`）
5. **取り込みは種別ごとのキーで重複を見分け、行を潰しそうなら止める**（下記
   「取り込みで行を捨てていた」）。EDA で件数を見るときは、保存データではなく
   API の応答を数える（保存データを数えて「API は1系列しか返さない」と誤った）
6. **毎週、保存データを API の応答と突き合わせる**（Check Data Store、土曜 10:40 JST に Routine が起動。
   `research/check_store_completeness.py`）。種別ごとに過去2年から数日を選んで叩き直し、
   その日の保存データの行数が API より少なければ赤にする。キーの誤り・取りこぼし・
   書き戻しの失敗のどれでも数が合わなくなる

## 2026-10-01 の一致チェックで出た progress_pct のずれ（原因と大きさ。2026-10-02 に調べた）

**結論: 先読み（公表前の値を学習に使う）ではない。原因は「同じ期の開示は最後の版を採用する」
規則（`quarterize_panel`）で、あとから出し直し（訂正）が来ると、学習だけがそれを知った状態で
計算される。** 差は2種類ある。

| | 何が起きるか | 学習の行 | 差（パーセンタイル点） |
|---|---|---:|---|
| (1) | 出し直しで元の版が順位の母集団から消え、その期より後に開示された行の順位が少し動く | 14,022行（64%） | 中央値 0.007 / 90% 0.026 / 最大 0.48（1点以上は0行） |
| (2) | 出し直しでその期の開示日が後ろへ移り、間の日の行が**一つ前の期**の数字に落ちる | 260行（1.19%） | 中央値 12.7 / 最大 73。片方だけ欠測 192行。学習が見る期は予測が見た期より中央値 92日古い |

数字は 2026-09-26 のデータ（学習 21,855行）。`research/probe_progress_pit.py` が、学習側を
`quarterize_panel` → `attach_fins` で作り直して `dataset.parquet` と全行一致することを確かめた上で、
版をすべて残した「その日に見えていた版」だけの計算と比べる。

経緯（公開ログの件数だけ。銘柄は書かない）

- 9/29 のチェック（9/24〜9/28 の行）: 全列一致。9/30（9/24〜9/29）: progress_pct が
  14行（239列で控えた 9/28・9/29 の 19行中）。10/1（9/24〜9/30）: **同じ14行**（30行中）で、
  9/30 の行は一致。つまり 9/30 の取り込みで入った決算（出し直し）が、それより前の行の順位を
  動かした。progress_pct 以外の列は一致しているので、行が見ている開示そのものは変わっていない
  （= (1) の型）
- 手元の 9/26 のデータで再現: 9月に出た 1Q/3Q の出し直し4件（元の開示の 124〜672日後）を
  除いて作り直すと、それより前に開示された 153,249行のうち 10,284行（6.7%）の progress_pct が
  変わる（最大 0.0065点）。progress_ratio は全行同じ。チェックは rtol 1e-6 で比べるので、
  この大きさでも「違う」と数える
- `lvs_ratio` / `lvs_ratio_chg`（各1行）: 大量保有報告書の同じ行の値があとから変わった
  （`lvs_days` は一致しているので別の報告ではない）。J-Quants 側の訂正。チェックの文書どおり
  記録して様子を見る。許容 1% は30行では1行で超えるので、下限の行数を上げるか「2行以上」を
  条件に足すかは運用者の判断

なぜ (2) が起きるか: 出し直しの版が「その期の開示」になり、開示日が出し直しの日に移る。
その日より前の行は、その期をまだ知らない扱い（一つ前の期の数字）になる。予測の時点では元の版が
見えていた。`days_since_disc` は版を潰す前の開示日で数えるので、この行でも一致している。

直し方の選択肢（運用者の判断待ち。10/2 時点で何も変えていない）

- **A: 版をすべて残す時点どおりのパネル。** 行が見るのは「その日までの最新の期の、その日までの

推奨は A（急がない。先に B を入れてチェックの誤報を止める手もある）。

## 2026-10-05 の一致チェックで出た rev_pct / rev_up の欠測（同じ日に2件ある業績予想の修正。2026-10-06 に調べた）

10/5（月）の予測（run 37326163279）の学習と予測の一致チェックで、過去の予測日の 1 行（9/28〜10/2 の 43 行中、
2.4%）だけ `rev_pct` と `rev_up` が「予測時は値あり・今は欠測」になった。許容 1.0% を超えたので step は赤、
run は continue-on-error で緑。原因を `research/exp/probe_rev_mismatch.py` で調べた
（run 37367494496 / 37368691872。ログに出すのは日付・種別・件数だけ）。

**原因: その銘柄は 2026-07-22 に業績予想の修正（EarnForecastRevision）を同じ日に 2 件出していて、

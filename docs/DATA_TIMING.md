# 特徴量の時点整合 —— 「その値を予測の時点で知りえたか」

特徴量の値は、**予測の時点で公表済みだったもの**でなければならない。学習用の
データセットは後から作り直すので、記録の日付（基準日・集計期間の末日）で結合すると、
学習だけが公表前の値を見ることになる。予測では同じ新しさの値は手に入らない。

各データの「使ってよい日」は `research/availability.py` の1か所で決め、
`tests/test_availability.py` が種別ごとに「公表日の前日までは前の値、公表日から
新しい値」を確かめる。日次予測は、その日に使った特徴量を控えて、翌日以降に
作り直した値と毎日比べる（`research/check_train_serve.py`、下記）。

## 結論を先に（2026-09-24）

- **2か所で公表前の値を学習に使っていた。** どちらも直した
  | 特徴量 | 公表 | 以前の結合 | 公表前の値を使っていた行 |
  |---|---|---|---:|
  | `credit_ratio`（週次の信用残） | 基準日（金曜）の翌週 第2営業日 | 基準日 | 38.5%（金曜の行の88%・月曜の83%） |
  | 投資部門別 `inv_*` 10列 | 集計期間の末日の約6日後（`PubDate`） | 集計期間の末日 | 85.7% |
- 同じ生データで直す前と後のデータセットを作って比べると、**違うのはこの12列だけ**
  （`inv_*` 10列が 85.69%、`credit_ratio` 38.48%、`credit_ratio_r` 30.47%）。
  行（21,856行）も、残りの341列（キーの Code・Date を除く353列のうち）も1つも変わらない
- **実運用ではずれがもっと大きかった。** 9/10〜9/18 に画面に出た信用倍率は、
  候補すべてが **8/28 の週**の値だった（取り込みの取りこぼしで 9/4・9/11 の週が
  まだ入っていなかった）。学習は同じ週（未公表）の値を見ていたので、ずれは最大3週間
- **修正で OOF の見込みはノイズの幅の中でしか動かなかった**（実験43。下の節）。
  修正で OOF の見込みがどう動くかは実験43で測った（`research/exp/e43_pit_fix.py`）。
  比べる「修正前」は `availability.LEGACY = True` で作り直したもので、直す前のコードで
  作ったデータセットと全セル一致することを確かめてある（21,856行 × 353列で違い0）
- **取り込みが行を捨てていた**（同じ日・同じ銘柄を1行に潰していた。決算短信 6,659行、
  大量保有・大株主・業種別の空売り比率・信用規制など）。キーを直して全期間を取り直し、
  保存データが API の応答と一致することを確かめた。取り直しで205列のうち150列の値が
  変わったが、**OOF の見込みはノイズの幅の中でしか動かなかった**（実験45。下の節）

## データごとの「使ってよい日」

日次予測は取り込みの後に走る（平日 21〜23時 JST が実績。遅れた日は翌日未明）。
その日の夜までに取り込めるものは当日から使ってよい。

「出た時刻」は Probe Update Time（`research/probe_update_time.py`）の実測。16:00 JST から
30分おきに当日ぶんを問い合わせ、最初に行が返った時刻を記録する（16:00 の値は
「16:00 の最初の問い合わせで既にあった」の意味で、それより前に出ていた可能性がある）。

| 種別 | 使ってよい日 | 根拠（出た時刻） | 状態 |
|---|---|---|---|
| 日足・業種別指数・TOPIX | 当日 | 日足 16:00、指数・TOPIX 16:30（9/18・9/24 とも同じ） | 確認済み |
| 銘柄マスタ（月次） | 当日 | 16:00 | 確認済み |
| 決算（`DiscDate`） | 当日 | 18:00 ごろ（9/18。9/24 は 18:02 に19行、20:03 まで増えず） | 確認済み。取り込みが 18:00 より前に走った日は翌日にずれるので、日次の食い違い確認で見る |
| 信用残（週次） | 基準日の翌週 **第2営業日** | JPX の週次公表 | **直した**。9/24 は連休明けの第1営業日で、9/18 ぶんは 20:00 までに出なかった（規則どおり）。第2営業日の 9/25 の Probe Update Time（run 36099557178、14:40 JST 起動・20:30 まで）は、ジョブの上限（350分）の 20:30:43 に殺され、出力も溜めたまま消えて何も残らなかった（`python3 -u` と `--max-minutes` で直した）。代わりに 9/25 夜の取り込みで 9/18 ぶんが入ったかを見る（入っていれば第2営業日の夜の予測に間に合う。公表の時刻そのものは測れていない） |
| 投資部門別（週次） | `PubDate` | J-Quants の公表日の列 | **直した**。9/24 は公表日が当日の行が 20:00 までに無かった（週次なので公表日でなかった可能性がある） |
| 信用規制 | `PubDate` | 16:30（9/24、322行） | 確認済み |
| 決算発表予定 | `PubDate`（`SchDate` では結合しない） | 16:00（9/24、93行） | 確認済み |
| バリュエーション | 当日（`Date`） | 16:00（9/24、4,450行） | 確認済み |
| 空売り比率（業種別。`short_ratio` は「その他」業種、`short_ratio_mkt` は全行の合計） | 当日（`Date`） | 16:30（9/24、34行） | 確認済み |
| 空売り残高報告（候補。実験44で採用しなかった。`docs/MODEL_ADOPTION_RULES.md` §9） | 公表日（`DiscDate`）の**翌営業日** | 18:02（9/24、1,340行） | 翌営業日のまま（`availability.SHORTSALE_SAME_DAY = False`）。夜の取り込みには間に合うが、取り込みが定刻（16:05 JST）どおりに起動した日には間に合わない。1日遅れる代わりに、取り込みの時刻に左右されない。取り込みは続ける |
| 大量保有・大株主・政策保有 | 提出日（`SubDate`） | 16:00 に最初の行が出て、**17:31 まで増えた**（大量保有 112→120→121→123行、大株主 37→45→48行、政策保有 36→44→47行。16:00 / 16:30 / 17:00 / 17:31 の値） | 当日のまま。17:30 より前に走った取り込みは一部しか取れないので、**今日の日は取得済みにしない**ようにした（下記） |

**9/24 の夜の取り込み（21:41 JST 起動）は、当日ぶんを実測の最終値どおりに保存していた。**
Release の保存データで 9/24 の行を数えると、バリュエーション 4,450・決算発表予定 93・
大量保有 123・大株主 48・政策保有 47・空売り比率 34・決算 19・空売り残高報告 1,340 行で、
Probe Update Time の 20:03 の値と全部一致した。信用規制だけは 0行で、これはその夜も
保存に失敗していたため（下の「保存に失敗し続けていた2種別」。全期間を取り直し中）。

**今日の日は取得済みにしない（2026-09-24 から）。** 取り込みは「叩きに行った日」を
取得済みとして記録し、次からはその日を問い合わせない。今までは今日の日も、行が
取れれば取得済みにしていた。EDINET の3種別は 16:00〜17:31 に行が増えるので、それより
前に取り込みが走ると、後から来た行を二度と取りに行かない。いまの取り込みは GitHub の
起動の遅れで毎日 21〜23時に走っているので実害はまだ無いが、定刻どおりに起動する日が
あれば起きる。今日の日は行が取れても記録せず、翌日の取り込みでもう一度取る
（`jq_bulk._record_fetched`。行のキーで重なりは1行になるので、取り直しても行は増えない）。
`tests/test_data_store.py` の `TestRecordFetched` が確かめる。

## 見逃さないための仕組み

1. **1か所で決める**: `research/availability.py` の `RULES`。取り込む種別を足したのに
   ここに行が無いと、`tests/test_availability.py` が落ちる
2. **結合の結果をテストする**: 公表日の前日の行に新しい値が入っていたら落ちる。
   直す前のコードに同じ入力を通すと、このテストは落ちる（確かめてある）
3. **毎日、予測に使った値と作り直した値を比べる**: 日次予測はその日の特徴量を控え
   （`live_features.parquet`、Release）、翌日以降の実行で、作り直したデータセットの
   同じ行と比べる。違いが許容（1%）を超えた列があれば、その段が赤になる
   （画面の更新は止めない）。公表前の値での結合、予測の時刻より後に届いたデータ、
   データの後からの訂正のどれでも値が変わるので、ここで捕まる
4. **CI は tests/ の全部を回す**（2026-09-24 から。`docs/OPERATIONS.md`）
5. **取り込みは種別ごとのキーで重複を見分け、行を潰しそうなら止める**（下記
   「取り込みで行を捨てていた」）。EDA で件数を見るときは、保存データではなく
   API の応答を数える（保存データを数えて「API は1系列しか返さない」と誤った）
6. **毎週、保存データを API の応答と突き合わせる**（Check Data Store、土曜 10:05 JST。
   `research/check_store_completeness.py`）。種別ごとに過去2年から数日を選んで叩き直し、
   その日の保存データの行数が API より少なければ赤にする。キーの誤り・取りこぼし・
   書き戻しの失敗のどれでも数が合わなくなる

いて、同じ日に同じ銘柄の行が複数あるデータを黙って1行に潰していた。取り込みと
同じ引数で8日ぶんを叩いて数えた（`research/probe_dedupe_keys.py`、件数と比だけ）:

影響
- **`short_ratio` / `short_ratio_20`（本番の205列）は「その他」業種の値だった。**
  残っていた1行は S33=9999 で、全市場ではなく「その他」（ほかの33行の合計の 4〜22%）。
  EDA の「API は1系列しか返さない」は、潰れた後の保存データを数えた誤り
  （`docs/MODEL_FEATURE_EDA.md` を訂正）。意味を黙って変えないよう計算は残し、
  市場全体は `short_ratio_mkt` として実験44で別に測る
- 決算（同じ日の決算短信と業績予想の修正のどちらか）、大量保有・大株主の件数や
  最新値、次の決算までの日数が、捨てた行のぶんずれていた。学習と予測は同じ
  潰れ方なので食い違いではないが、情報を捨てていた。取り直した前後を実験45で比べる

直したこと
- キーを種別ごとに決めた（`data_store.ROW_KEYS`。どれも API の応答で一意になることを
  実測で確かめた）。**登録の無い種別は保存しない**
- 今回取った行の中でキーが重なり中身が違えば、保存せずに止める（キーの誤りで
  別々の行を潰すのを、その場で捕まえる）
- `tests/test_data_store.py`: 業種34行・同じ日の2人の提出者・同じ日の2つの開示・
  報告者ごとの空売り残高が全部残ること、取り込む全種別にキーがあること。
  直す前のコードではこのうち8本が落ちる（確かめてある）
- 捨てていた5種別（fins / earndate / lvshld / mjrshld / shortratio）は、取り直す前の
  生データを別のタグに写してから（Snapshot Raw Data、タグ `pre-dedupe-20260924`）、
  全期間を取り直す

**キーの決め方でもう一度誤った（同じ日のうちに直した）。** EDINET の3種別のキーを最初は
DocId にしたが、一意かを1日ぶんずつしか確かめておらず、**日をまたいだ**一意性を見て
いなかった。同じ文書が別の提出日でも出る（大株主で612文書）ため、全期間の取り直しで
今回取った行の中でキーが重なり、上の「保存しない」が働いて保存を止めた（大量保有
34行・大株主 1,275行。run 35968485054。データは失っていない）。
158日ぶんをまとめた実測（`probe_dedupe_keys.py --span 150`）で、どの種別も日付列が
問い合わせた日と常に一致し（違う行 0）、(DocId, SubDate) で一意になることを確かめて、
キーを直した。全期間の取り直しで得た行数は 大量保有 75,690行（保存 55,828行、26% を
捨てていた）、大株主 81,452行（77,730行）、決算 190,696行（保存 180,671行、5.3% を捨てていた。8日ぶんの実測の 3.1% より多い）。

**保存に失敗し続けていた2種別（2026-09-23 までの毎日）。** 大量保有報告書と信用規制は、
入れ子の列（Hldrs / PubReason）に "" や "-" が混ざった日に parquet が書けず
（`_sanitize` が入れ子かを最初の値だけで決めていた）、毎日の取り込みで全期間を取り直しては
保存に失敗していた（1回あたり約80分）。ジョブは緑で、ログの [warn] だけだった。
信用規制の保存データは 2026 年が 9/01〜9/18 しか無く（1〜8月が欠けている）、PubReason が
文字列に潰れていた。入れ子の判定を全部の値で行うように直し、保存の失敗は実行の画面の
注記（::error::）と manifest の `save_failures` に残すようにした。信用規制は
(PubDate, Code) でも全期間では一意にならなかったので、行そのものをキーにし、
保存データを消して全期間を取り直した（2026-09-24 夜、run 36016684765）。全期間で
447,854行、2026年は1〜9月がそろい（45,599行）、PubReason はすべて入れ子のまま、
まったく同じ行の重なりは0。

**取り直した後の突き合わせ（Check Data Store、run 36022554520）:** 取り込む全種別で、
過去2年から選んだ日（日足2日、ほかは5日ずつ）の保存データの行数が API の応答と
すべて一致した（信用規制は 2026年の5日で 262〜296行）。取り直す前の突き合わせ
（run 36011902289）では、信用規制だけが同じ期間の5日すべてで保存0行（API は 264〜307行）
だった。

### 実験45: 取り直した前後で OOF はどう変わったか（2026-09-24、run 36022561417）

**結論: 205列のうち150列の値が変わったが、分離力も運用の規則での取引もノイズの幅の中で
しか動かなかった。** これまでの OOF の見込みが、捨てていた行のせいで目に見えて
ずれていたわけではない。取り直しは見込みの数字のためではなく、捨てていた情報を
戻すためなので、そのまま残す。

作り: A は取り直す前の生データ（Snapshot Raw Data、タグ `pre-dedupe-20260924`。決算・
決算発表予定・大量保有・大株主・業種別の空売り比率・信用規制の6種別）、B は取り直した後。
ほかの種別・コード・パラメータは同じ（本番の205列・本番のパラメータ・ブースティング
3モデル・種3つの平均、窓の境界を 0/2/4か月ずらした3通りの計32窓。`research/exp/e45_dedupe_fix.py`）。
行は前後とも 21,867行で、出入りは無い。

**値が変わった列が多い理由（確かめた）。** 決算は、同じ銘柄が同じ日に出した複数の開示を
1行に潰していた。取り直しで戻った 10,025行のうち **6,659行が決算短信**（残りは業績予想の
修正 2,883行、配当予想の修正 483行）で、潰したときに決算短信の方を捨て、修正の方を
残していた日が多かった。実績のある四半期は 147,947 → 153,506（+5,559、3.6%）に増え、
前にしか無い四半期は0。前年同期比・3四半期前との差・加速などは1つの四半期の欠けで

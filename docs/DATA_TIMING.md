# 特徴量の時点整合 —— 「その値を予測の時点で知りえたか」

特徴量の値は、**予測の時点で公表済みだったもの**でなければならない。学習用の
データセットは後から作り直すので、記録の日付（基準日・集計期間の末日）で結合すると、
学習だけが公表前の値を見ることになる。予測では同じ新しさの値は手に入らない。

各データの「使ってよい日」は `research/availability.py` の1か所で決め、
`tests/test_availability.py` が種別ごとに「公表日の前日までは前の値、公表日から
新しい値」を確かめる。日次予測は、その日に使った特徴量を控えて、翌日以降に
作り直した値と毎日比べる（`research/check_train_serve.py`、下記）。

## 結論を先に（2026-09-24）

- **2か所で公表前の値を学習に使っていた。** どちらも直した
  | 特徴量 | 公表 | 以前の結合 | 公表前の値を使っていた行 |
  |---|---|---|---:|
  | `credit_ratio`（週次の信用残） | 基準日（金曜）の翌週 第2営業日 | 基準日 | 38.5%（金曜の行の88%・月曜の83%） |
  | 投資部門別 `inv_*` 10列 | 集計期間の末日の約6日後（`PubDate`） | 集計期間の末日 | 85.7% |
- 同じ生データで直す前と後のデータセットを作って比べると、**違うのはこの12列だけ**
  （`inv_*` 10列が 85.69%、`credit_ratio` 38.48%、`credit_ratio_r` 30.47%）。
  行（21,856行）も、残りの341列（キーの Code・Date を除く353列のうち）も1つも変わらない
- **実運用ではずれがもっと大きかった。** 9/10〜9/18 に画面に出た信用倍率は、
  候補すべてが **8/28 の週**の値だった（取り込みの取りこぼしで 9/4・9/11 の週が
  まだ入っていなかった）。学習は同じ週（未公表）の値を見ていたので、ずれは最大3週間
- **修正で OOF の見込みはノイズの幅の中でしか動かなかった**（実験43。下の節）。
  修正で OOF の見込みがどう動くかは実験43で測った（`research/exp/e43_pit_fix.py`）。
  比べる「修正前」は `availability.LEGACY = True` で作り直したもので、直す前のコードで
  作ったデータセットと全セル一致することを確かめてある（21,856行 × 353列で違い0）

## データごとの「使ってよい日」

日次予測は取り込みの後に走る（平日 21〜23時 JST が実績。遅れた日は翌日未明）。
その日の夜までに取り込めるものは当日から使ってよい。

| 種別 | 使ってよい日 | 根拠 | 状態 |
|---|---|---|---|
| 日足・業種別指数・TOPIX | 当日 | 16:30 JST までに出る（実測 2026-09-18） | 確認済み |
| 銘柄マスタ（月次） | 当日 | 16:00 JST より前（実測） | 確認済み |
| 決算（`DiscDate`） | 当日 | 18:00 JST ごろ出る（実測）。9/18 の取り込み（21:12 JST）には当日の20行が入っていた | 確認済み。取り込みが 18:00 より前に走った日は翌日にずれるので、日次の食い違い確認で見る |
| 信用残（週次） | 基準日の翌週 **第2営業日** | JPX の週次公表 | **直した**。J-Quants が第2営業日の夜に間に合うかは probe（`margin_fri`）で確かめる |
| 投資部門別（週次） | `PubDate` | J-Quants の公表日の列 | **直した** |
| 信用規制 | `PubDate` | 公表日の列 | 当日の夜に出るかを probe で確かめる |
| 決算発表予定 | `PubDate` | 公表日の列（`SchDate` では結合しない） | 同上 |
| バリュエーション | 当日（`Date`） | — | **未確認**。probe で当日の夜に出るかを測る |
| 空売り比率（業種別。`short_ratio` は「その他」業種、`short_ratio_mkt` は全行の合計） | 当日（`Date`） | — | **未確認**。同上 |
| 空売り残高報告（新規の候補） | 公表日（`DiscDate`）の**翌営業日** | 当日の夜に間に合うかを probe で測るまで | 測ったら `availability.SHORTSALE_SAME_DAY` で当日に寄せる |
| 大量保有・大株主・政策保有 | 提出日（`SubDate`） | — | **未確認**。J-Quants に載る時刻を probe で測る |

未確認の4種は、2026-09-24 16:00〜20:00 JST の実測（Probe Update Time）と、その夜の
取り込みのログで決める。当日の夜の取り込みに間に合わないものは、翌営業日から
使うように `research/availability.py` を直す。

## 見逃さないための仕組み

1. **1か所で決める**: `research/availability.py` の `RULES`。取り込む種別を足したのに
   ここに行が無いと、`tests/test_availability.py` が落ちる
2. **結合の結果をテストする**: 公表日の前日の行に新しい値が入っていたら落ちる。
   直す前のコードに同じ入力を通すと、このテストは落ちる（確かめてある）
3. **毎日、予測に使った値と作り直した値を比べる**: 日次予測はその日の特徴量を控え
   （`live_features.parquet`、Release）、翌日以降の実行で、作り直したデータセットの
   同じ行と比べる。違いが許容（1%）を超えた列があれば、その段が赤になる
   （画面の更新は止めない）。公表前の値での結合、予測の時刻より後に届いたデータ、
   データの後からの訂正のどれでも値が変わるので、ここで捕まる
4. **CI は tests/ の全部を回す**（2026-09-24 から。`docs/OPERATIONS.md`）
5. **取り込みは種別ごとのキーで重複を見分け、行を潰しそうなら止める**（下記
   「取り込みで行を捨てていた」）。EDA で件数を見るときは、保存データではなく
   API の応答を数える（保存データを数えて「API は1系列しか返さない」と誤った）
6. **毎週、保存データを API の応答と突き合わせる**（Check Data Store、土曜 10:05 JST。
   `research/check_store_completeness.py`）。種別ごとに過去2年から数日を選んで叩き直し、
   その日の保存データの行数が API より少なければ赤にする。キーの誤り・取りこぼし・
   書き戻しの失敗のどれでも数が合わなくなる

## 取り込みで行を捨てていた（2026-09-24 に見つけて直した）

空売り残高報告の取り込みを書く途中で見つけた。年別ファイルへのマージ
（`data_store.merge_into_years`）が**全種別を「同じ日・同じ銘柄」で重複除去**して
いて、同じ日に同じ銘柄の行が複数あるデータを黙って1行に潰していた。取り込みと
同じ引数で8日ぶんを叩いて数えた（`research/probe_dedupe_keys.py`、件数と比だけ）:

| 種別 | API の行 | 残っていた行 | 捨てていた割合 | 正しいキー（実測で一意） |
|---|---:|---:|---:|---|
| 業種別の空売り比率 | 272 | 8 | **97.1%** | Date + S33（銘柄の列が無く「同じ日」で潰れた） |
| 大量保有報告書 | 227 | 194 | 14.5% | DocId + SubDate |
| 大株主 | 3,130 | 2,867 | 8.4% | DocId + SubDate |
| 決算発表予定 | 1,414 | 1,330 | 5.9% | PubDate + Code + FQName + SchDate |
| 決算 | 2,250 | 2,180 | 3.1% | DiscNo（開示番号） |
| 日足・信用残・バリュエーション・信用規制・政策保有 | — | — | 0% | 今までどおり |
| 空売り残高報告（新規） | 5,348 | （3,467） | （35.2%） | 行そのもの（ID が無く、どの列の組でも一意にならない） |

影響
- **`short_ratio` / `short_ratio_20`（本番の205列）は「その他」業種の値だった。**
  残っていた1行は S33=9999 で、全市場ではなく「その他」（ほかの33行の合計の 4〜22%）。
  EDA の「API は1系列しか返さない」は、潰れた後の保存データを数えた誤り
  （`docs/MODEL_FEATURE_EDA.md` を訂正）。意味を黙って変えないよう計算は残し、
  市場全体は `short_ratio_mkt` として実験44で別に測る
- 決算（同じ日の決算短信と業績予想の修正のどちらか）、大量保有・大株主の件数や
  最新値、次の決算までの日数が、捨てた行のぶんずれていた。学習と予測は同じ
  潰れ方なので食い違いではないが、情報を捨てていた。取り直した前後を実験45で比べる

直したこと
- キーを種別ごとに決めた（`data_store.ROW_KEYS`。どれも API の応答で一意になることを
  実測で確かめた）。**登録の無い種別は保存しない**
- 今回取った行の中でキーが重なり中身が違えば、保存せずに止める（キーの誤りで
  別々の行を潰すのを、その場で捕まえる）
- `tests/test_data_store.py`: 業種34行・同じ日の2人の提出者・同じ日の2つの開示・
  報告者ごとの空売り残高が全部残ること、取り込む全種別にキーがあること。
  直す前のコードではこのうち8本が落ちる（確かめてある）
- 捨てていた5種別（fins / earndate / lvshld / mjrshld / shortratio）は、取り直す前の
  生データを別のタグに写してから（Snapshot Raw Data、タグ `pre-dedupe-20260924`）、
  全期間を取り直す

**キーの決め方でもう一度誤った（同じ日のうちに直した）。** EDINET の3種別のキーを最初は
DocId にしたが、一意かを1日ぶんずつしか確かめておらず、**日をまたいだ**一意性を見て
いなかった。同じ文書が別の提出日でも出る（大株主で612文書）ため、全期間の取り直しで
今回取った行の中でキーが重なり、上の「保存しない」が働いて保存を止めた（大量保有
34行・大株主 1,275行。run 35968485054。データは失っていない）。
158日ぶんをまとめた実測（`probe_dedupe_keys.py --span 150`）で、どの種別も日付列が
問い合わせた日と常に一致し（違う行 0）、(DocId, SubDate) で一意になることを確かめて、
キーを直した。全期間の取り直しで得た行数は 大量保有 75,690行（保存 55,828行、26% を
捨てていた）、大株主 81,452行（77,730行）。

## 以前に書いたことの訂正

`research/jq_bulk.py` の取り込みの表には「日付列は『その行をいつ知りえたか』を
表すものを選ぶ」と書いてあり、EDINET は提出日、信用規制は公表日にしていた。
それなのに投資部門別は集計期間の末日、信用残は基準日のままで、原則が守られて
いなかった。テストは EDINET と信用規制だけを確かめていて、この2つを見ていなかった。
